# TableIR → GraphIR conversion — implementation plan

2026-02-11. Plan for the TableIR → GraphIR transformation (`resolve_molecule`, etc.). This conversion is the main semantic validation step: TableIR is a permissive container; GraphIR is strictly validated. Reference: [44-unified-ir-graph-models-2026-01-14.md](44-unified-ir-graph-models-2026-01-14.md).

---

## 1. Data model and nomenclature

### 1.1 Data model

- Continues the TableIR split between basic and extended molecules / reactions but
  splits extended types further into query molecule, variable molecule structs, etc.
- Invariant: molecular graph is connected. Potentially create Supermolecule as
  multi-molecule container in the future. Molecule resolution from disconnected graph
  results in error.
- Moves aromaticity and stereochemistry information into molecule-level objects instead
  of keeping in individual atoms and bonds. Objects are generated with validation.
- Structures are generated via validation step (which could be no-op) from TableIR.
  TableIR could also be used as a builder (instead of a separate molecule builder)?
- Planning for mutable design for now because of efficiency considerations. Should
  investigate immutable data structures with structural sharing after the first
  design pass. That would allow to use Graph (instead of StableGraph, which may be
  more space-efficient).
- Generally feature-rich, potential duplicate data allowed where recalculation is
  impractical, invariants enforced via careful API design.
- Circular dependency problem addressed by using atom, bond indices instead of
  references. Internal graph structure is petgraph::StableGraph, which maintains
  the node and edge indices across deletions (except for indices of deleted nodes
  and edges, which become invalid).

### 1.2 Nomenclature

- resolve\_\* - function names, convey shallow → deep, validated; comp-sci connotation
- `ResolutionError` — error type; covers valence, topology, aromaticity, stereo, atom mapping.
- Variants (preliminary): `ValenceViolation`, `TopologyError`, `AromaticityError`, `StereochemistryError`, `AtomMappingError`, `UnsupportedFeature`, etc.

## 2. Conversion pipeline overview

```
TableIR (Molecule | ExtendedMolecule | Reaction | ExtendedReaction)
    → [Topology validation]    (atom/bond index checks; self-loops; parallel edges)
    → [Valence validation]     (configurable)
    → [Aromaticity validation] (configurable)
    → [Stereochemistry validation] (configurable)
    → [Atom mapping validation] (reactions only)
    → GraphIR (Molecule | Reaction)
```

Each step is a pass; configuration controls which runs and with what strictness. Order matters: topology and valence before aromaticity; aromaticity before stereo when bond order affects stereo.

## 3. Key conversion parts

### 3.1 Topology validation

- **Validation**: Atom and bond index validity (indices in range, no dangling refs); self-loops; parallel edges. Forms a valid graph.
- **Multi-fragment**: No explicit multi-fragment structures in GraphIR. Topology validation is more relevant for CTab (MOL/SDF) inputs than for SMILES, where components are made explicit by `.`. CTab may have disconnected fragments in a single block; resolution rejects or requires a single connected component per molecule (TBD per use case).
- **Extended molecules** (out of scope for now): R-groups, S-groups, wildcards, links — to be handled or rejected when `resolve_extended_molecule` is implemented.

#### Topology resolver steps and options

**1. Connectedness check**

- **Requirement**: Single connected component per molecule (configurable: error if `component_count() > 1`). petgraph allows disconnected graphs; this is a semantic rule for GraphIR.
- **petgraph**: `petgraph::algo::connected_components(g)` returns the **count** only (`usize`). It does **not** return the partition (list of components). Complexity: amortized O(|E| + |V|log|V|).
- **Getting the list of components**: Either (a) use `petgraph::unionfind::UnionFind`: create `UnionFind::new(n)`, for each edge `union(a, b)`, then `into_labeling()` gives a representative per node; group nodes by representative to get `Vec<Vec<NodeId>>`. Or (b) run BFS/DFS from each unvisited node and collect one component per DFS tree. Both are O(V+E). Union-Find is O(E α(V)); one DFS pass is O(V+E). No need for a “more efficient” algorithm for undirected connected components — both are standard and efficient.
- **Implementation note**: TableIR already has `component_count()` and `component_atom_indices()` (UnionFind over bonds + multicenter bonds). Topology can run the connectedness check on the TableMolecule before building the GraphIR graph, and error if > 1 component when config requires connected. Alternatively build the graph first and use `petgraph::algo::connected_components(&graph)` for the count; if we need the partition on the graph side, use `petgraph::unionfind::UnionFind` on node indices or a single DFS pass.

**2. Self-loops and parallel edges**

- **Requirement**: Both cause topology errors (reject).
- **Self-loop**: A bond with the same atom as both endpoints. On TableIR: for each bond, reject if `bond.atoms.first() == bond.atoms.second()`. On a built graph: an edge with `edge_endpoints(e)` satisfying `a == b`.
- **Parallel edges**: Two or more bonds between the same pair of atoms. On TableIR: collect canonical pair `(min(a,b), max(a,b))` per bond; if any pair appears more than once, error. On a built graph: for each unordered pair of nodes, `graph.edges_connecting(a, b).count() > 1` → error.
- **Where to check**: Can validate on TableIR (bond list) before building the graph, so we fail fast without constructing the graph. Or validate after building; both are straightforward.

**3. Ring system detection** -> omitted for now

- **Purpose**: Needed for downstream (aromaticity phase). Aromaticity checks ring membership and Kekulé feasibility; ring detection is a prerequisite.
- **SSSR**: Smallest Set of Smallest Rings — common in cheminformatics (RDKit, OpenBabel). Not unique for fused systems; multiple valid SSSRs can exist for the same graph. Used for parity with RDKit.
- **petgraph**: Does **not** provide SSSR or a minimum cycle basis. It provides `is_cyclic_undirected`, `is_cyclic_directed`, and a `Cycle` struct (used as an error type when a cycle is detected where it is not allowed). So we must either implement ring/cycle enumeration ourselves or depend on another crate.
- **Options**: (a) Implement SSSR (e.g. Horton’s algorithm, or a path-based approach); (b) use a minimum cycle basis (MCB) instead of SSSR — see e.g. discussion 39 (avoid ambiguity in fused systems); (c) add a dependency that provides SSSR/MCB if one exists in the Rust ecosystem. For topology phase we only need “some” ring set for downstream; the exact choice (SSSR vs MCB) can be configurable or fixed when we implement the aromaticity phase.
- **TableIR rings**: `table_ir::Molecule` has `rings: Vec<Ring>`, but that is SMILES ring-closure metadata (start/end atom of each closure), not a computed SSSR. So we cannot reuse it as the full ring set; we need a separate ring-finding step on the graph (or on TableIR bonds) for aromaticity.

### 3.2 Valence validation

- **Configurable**: On/off; policy (Error / Warn / Ignore).
- **Inputs**: Element, charge, implicit H, unpaired electrons, bond sum (incl. dative contribution).
- **Approach** (umol): Match against **defined valence states** (AtomSpec / ValenceState), not simple allowed-valence lists. Equality check: `target_valence == unpaired + bond_sum + implicit_H` (and optionally lone pairs, donated/accepted pairs for dative).
- **Comparison with RDKit/CDK/Indigo**:
  - RDKit: `calcExplicitValence` / `calcImplicitValence`; allowed valence lists per element; special cases for aromaticity, hypervalent P/S, etc. Known to miss some violations and to be too permissive in edge cases.
  - CDK: Similar list-based model with element-specific rules.
  - Indigo: Valence check with configurable rules.
  - **umol stance**: These are informative (RDKit's atomic_data.cpp, etc.) but too restrictive for non-standard states. We prefer a state-table approach: if a state is defined, it's allowed; if not, configurable reject/warn. Supports pentavalent P, carbenes, low-spin Fe(II), etc. when explicitly defined.
- **Config**: `ValenceConfig` (see `valence.rs`); support multiple schemes (simple organic vs. extended state table) via trait or enum.

### 3.3 Aromaticity validation

- **Configurable**: On/off; model (null, verify-only, Hückel, etc.).
- **Background**: [14](14-aromaticity-2025-03-08.md) (state of the art); [41](41-opensmiles-aromaticity-2025-10-01.md) (HMO, Clar, Kekulé options).
- **Inputs**: Aromatic atom/bond flags from parser; graph topology; optional Kekulé assignment.
- **Model**: Per [39](39-opensmiles-semantic-issues-2025-09-30.md), [41](41-opensmiles-aromaticity-2025-10-01.md): verify lowercase/`:` requests are satisfiable (atoms in rings, Kekulé exists, optional Hückel 4n+2). Do not silently override; emit deterministic errors.
- **Current state**: `lint_gir_aromaticity` in `io/smiles/linter/gir.rs` does a minimal check (aromatic atom degree). Full Kekulé/Hückel is not implemented. Separate pass design needed.
- **Order**: After valence (or interleaved where bond order affects implicit H). Before stereo when aromatic affects bond order interpretation.

### 3.4 Stereochemistry validation

- **Configurable**: On/off; strictness.
- **Inputs**: Chirality, wedge, bond stereo from TableIR; graph topology.
- **Model**: Per [49](49-stereochemistry-encoding-2026-01-29.md): ordering-independent semantics using ports (half-edges). Validation ensures consistency (e.g. sufficient substituents for double-bond stereo, no conflicting wedges).
- **Current state**: `lint_gir_stereo` is a stub. Dedicated pass to be implemented; keep steps separate from topology/valence/aromaticity.
- **Reference**: CDK/RDKit stereo perception; we want configurable strictness and clear diagnostics.

### 3.5 Atom mapping validation (reactions only)

- **Checks**: Class numbers consistent across sides; no duplicate mappings that violate chemistry; optional coverage checks.
- **Current state**: `collect_atom_mapping` builds the mapping; no validation of consistency. Add a validation pass that can emit `ResolutionError::AtomMappingError`.

### 7.2 Aromatic systems and multicenter bonds in GraphIR

Aromatic systems and multicenter bonds are **hyperedges**: they connect more than two atoms. petgraph only supports ordinary (two-node) edges. Four representation options were considered:

| Option                | Description                                                                                                                                | Pros                                                                                                       | Cons                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| A. Side tables        | Separate `Vec<AromaticSystem>`, `Vec<MulticenterBond>` on Molecule, referencing atoms by `NodeIndex`                                       | Simple; no graph library changes; familiar (TableIR pattern)                                               | Hyperedge topology not integrated into graph algorithms; manual consistency |
| B. Bipartite encoding | Virtual nodes in StableGraph for each system; atom→system edges with contribution metadata                                                 | Native traversal; graph algorithms work directly                                                           | Pollutes every algorithm with node-type filtering; enum nodes/edges         |
| C. Hypergraph library | Dedicated Rust hypergraph crate                                                                                                            | Mathematically correct                                                                                     | Immature ecosystem; likely need to maintain it; overkill for current needs  |
| D. Layered model      | One `StableGraph<Atom, Bond>` for ordinary bonds; separate typed layers for aromatic systems and multicenter bonds referencing `NodeIndex` | Clean separation; main graph stays simple; layers are add/remove without modifying graph; easy to validate | Need manual consistency checks on mutation                                  |

**Decision: Option D (layered model).**

Rationale:

1. **Semantically correct.** Aromatic systems and multicenter bonds are molecule-level properties, not edge properties. Representing them as molecule-level layers is more faithful than forcing them into the edge model.
2. **Avoids the RDKit problem at the right level.** RDKit's aromaticity mess stems from conflating aromatic state into per-atom/per-bond flags with inconsistent validity rules. The layered model avoids this by design: atoms and bonds carry no aromatic/multicenter flags; the layers do.
3. **Bipartite encoding is premature.** The only benefit — native traversal of hyperedges — matters for specialized algorithms (aromatic ring perception, Kekulé assignment) that can work directly on the layer data. A bipartite _view_ can be added later without changing the core.
4. **`StableGraph` `NodeIndex` is stable across deletions.** Layer→graph references by `NodeIndex` are safe. Validate on mutation (atom insertion/removal invalidates layers).

#### Concrete structure

```rust
struct Molecule {
    graph: StableGraph<Atom, Bond>,
    aromatic_systems: Vec<AromaticSystem>,
    multicenter_bonds: Vec<MulticenterBond>,
    // stereo, positions, metadata ...
}
```

**Aromatic systems.** Represented as sets of per-atom contributions. Each atom contributes a fixed `aromatic_valence > 0` to the system. The system as a whole is validated (ring membership, Kekulé feasibility, optional Hückel 4n+2).

```rust
struct AromaticSystem {
    contributions: Vec<AromaticContribution>,
}

struct AromaticContribution {
    atom: NodeIndex,
    aromatic_valence: u8,
}
```

**Multicenter bonds.** Broader than aromatic systems: typically not π systems, contributions are not necessarily fixed per-atom valences. Represented as sets of atom groups with electron contributions (same conceptual model as TableIR `MulticenterBond` but using `NodeIndex` instead of `u32`).

#### Three valence types on Atom

The Atom struct carries three valence fields:

- `valence: u8` — ordinary two-center bond valence (sum of incident bond orders + implicit H + unpaired electrons).
- `aromatic_valence: u8` — electrons contributed to aromatic systems. Nonzero only for atoms participating in an aromatic system.
- `multicenter_valence: u8` — electrons contributed to multicenter bonds. Nonzero only for atoms participating in a multicenter bond.

Ordering of generality: ordinary bond < aromatic system < multicenter bond. The most common case (ordinary bonds) is separated for efficiency and clarity.

#### Consistency discipline

Layers reference the graph by `NodeIndex`. Invariants:

- All `NodeIndex` values in layers must be valid in the graph.
- Aromatic system atoms must form rings in the graph.
- Multicenter bond atoms must all be present in the graph.
- Atom valence fields must be consistent with the graph topology and layers.

Validation is enforced on construction (resolution from TableIR) and on mutation (molecule editing API). Layers are invalidated on structural graph changes; re-validation is explicit.

## 8. Aromatic systems and multicenter bonds: analysis and revised design

### 8.1 Aromatic systems: per-atom inference and charge

Per-atom `aromatic_valence` can be inferred from element type, hydrogen count, and bond connectivity:

| Molecule           | Atom         | σ bonds    | H   | aromatic_valence | Rule                         |
| ------------------ | ------------ | ---------- | --- | ---------------- | ---------------------------- |
| Benzene            | C            | 3 (2C+H)   | 0   | 1                | C in aromatic ring: always 1 |
| Naphthalene        | C (junction) | 3 (3C)     | 0   | 1                | Same                         |
| Furan              | O            | 2 (2C)     | 0   | 2                | O/S: lone pair → π           |
| Pyrrole            | N            | 2 (2C)     | 1   | 2                | N with H: lone pair → π      |
| Pyridine           | N            | 2 (2C)     | 0   | 1                | N without H, 2σ: 1e in π     |
| N-methylpyridinium | N⁺           | 3 (2C+CH₃) | 0   | 1                | N⁺ with 3σ: 1e in π          |
| Pyridine N-oxide   | N⁺           | 3 (2C+O⁻)  | 0   | 1                | Same                         |
| Imidazole N1       | N            | 2 (2C)     | 1   | 2                | Pyrrole-type                 |
| Imidazole N3       | N            | 2 (2C)     | 0   | 1                | Pyridine-type                |

For all neutral aromatics: total π = Σ aromatic_valence satisfies 4n+2 directly.

**Charged rings** require a system-level charge term:

| System                 | Σ aromatic_valence | Formal charge | total π = Σ − charge | Hückel      |
| ---------------------- | ------------------ | ------------- | -------------------- | ----------- |
| Cp⁻ (C₅H₅⁻)            | 5                  | −1            | 6                    | 4n+2, n=1 ✓ |
| Tropylium (C₇H₇⁺)      | 7                  | +1            | 6                    | 4n+2, n=1 ✓ |
| COT²⁻ (C₈H₈²⁻)         | 8                  | −2            | 10                   | 4n+2, n=2 ✓ |
| Cyclopropenyl⁺ (C₃H₃⁺) | 3                  | +1            | 2                    | 4n+2, n=0 ✓ |

The charge is not assignable to any individual atom — it is delocalized over the ring. The formula is: `total_π = Σ(aromatic_valence) − formal_charge_of_system`, where `formal_charge_of_system = Σ atom.charge for atoms in the ring`.

**Conclusion**: AromaticSystem needs a `charge: i8` field in addition to per-atom contributions. The charge can be inferred by summing formal charges of ring atoms.

### 8.2 Multicenter bonds: data availability from CX

**What CX provides**: The CX encoding `m:center:ligand.ligand,...` gives only the atom topology — which atoms participate in which multicenter bond, grouped into a "center" atom and "ligand" atom set. **No electron counts are available** from the CX format. The table_ir stores 0 as placeholder for all electron counts.

**What the correct per-atom contributions would be** (for reference):

| System        | Bond  | Per-atom contributions (correct) | Total e |
| ------------- | ----- | -------------------------------- | ------- |
| B₂H₆ bridge   | 3c-2e | (B₁, 1), (H_br, 1), (B₂, 0)     | 2       |
| XeF₂          | 3c-4e | (Xe, 2), (F₁, 1), (F₂, 1)       | 4       |
| Ferrocene Cp  | haptic | Each C: 1, Fe: 0. Charge −1       | 6       |
| Cr(C₆H₆)₂ Bz  | haptic | Each C: 1, Cr: 0. Charge 0        | 6       |
| Ni(η³-allyl)₂ | haptic | Each C: 1, Ni: 0. Charge −1       | 4       |

None of this information is encoded in the CX format. Heuristic inference is not the approach we want to take.

**Consequence for GraphIR**: The graph_ir `MulticenterBond` must be constructible with topology-only information (atom sets). Per-atom electron contributions and charge are populated during the valence resolution phase, if sufficient information is available. The `MulticenterBondBuilder` enables this staged construction.

### 8.3 Data model

Both aromatic systems and multicenter bonds share the same fully-resolved data shape:

```
per-atom contributions: Vec<(AtomIndex, u8)>
charge: i8
total_electrons = Σ per_atom − charge
```

The current GraphIR structures differ:

- `AromaticSystem`: per-atom `(AtomIndex, aromatic_valence)`, **missing charge**.
- `MulticenterBond`: per-set `(Vec<AtomIndex>, electrons)`, **per-atom split missing and electrons unavailable from input**.

**Revised design**:
- `AromaticSystem`: add `charge: i8` field. Per-atom contributions remain as-is. Charge is inferrable by summing formal charges of ring atoms.
- `MulticenterBond`: replace per-set grouping with per-atom `(AtomIndex, u8)` + system `charge: i8`. Per-atom contributions and charge are **not available from CX input** and must be populated during valence resolution.
- `MulticenterBondBuilder`: enables staged construction — topology-only at the topology phase, electron contributions added at the valence phase.
- Table_ir `MulticenterBond`/`MulticenterSet` unchanged.

### 8.4 What cannot be reliably inferred

1. **Non-standard per-atom splits**: Mixed-element sets with unusual contributions (rare).
2. **Metal contributions ≠ 0**: Most organometallic complexes have metal contributing 0e; exceptions (metal-metal bonds with bridging ligands) require additional rules.
3. **Open-shell systems**: Allyl radical (3 C, 3e, neutral) — the structure can represent it; whether to accept it is a validation policy question, not a data model question.
4. **Ambiguous charge partition**: Zwitterionic organometallics where the ionic vs covalent model gives different per-atom splits. The total electron count is unambiguous; only the split changes.

### 8.5 Remaining open questions

- Total molecular spin state multiplicity missing from the GraphIR molecule struct.
- Open-shell aromatic/delocalized systems: representable but validation rules TBD.

## 9. Revised AromaticSystem and MulticenterBond: implementation plan

### 9.1 AromaticSystem (graph_ir::aromatic)

Change: add `charge: i8` field.

```rust
struct AromaticSystem {
    contributions: Vec<AromaticContribution>,  // (AtomIndex, aromatic_valence)
    charge: i8,
}
// total_π = Σ aromatic_valence − charge
```

- `AromaticContribution` unchanged: `(AtomIndex, u8)`.
- Constructor: `AromaticSystem::new(contributions, charge)`.
  - `debug_assert!` that `Σ aromatic_valence as i16 - charge as i16 >= 0`.
- `electron_count() -> u8`: returns `Σ aromatic_valence − charge` (compute via `i16`, cast to `u8`).
- Existing methods (`atom_count`, `contains_atom`, `atoms`) unchanged.

### 9.2 MulticenterBond (graph_ir::multicenter)

Two-level structure: a multicenter bond contains one or more multicenter sets, each consisting
of per-atom contributions. This preserves the set grouping from the input (center vs ligand sets)
while adding per-atom electron data where available.

```rust
struct MulticenterContribution {
    atom: AtomIndex,
    electrons: Option<u8>,  // None when not yet resolved
}

struct MulticenterSet {
    contributions: Vec<MulticenterContribution>,  // canonicalized by atom index
    charge: i8,
}
// set total_electrons = Σ per_atom − charge (only when all contributions resolved)

struct MulticenterBond {
    sets: SmallVec<[MulticenterSet; 4]>,  // canonicalized by set ordering
}
// total_electrons = Σ set.total_electrons
```

- Constructors: `MulticenterSet::new(contributions, charge)`, `MulticenterBond::new(sets)`.
  - `debug_assert!` on non-negative electron total when all contributions are `Some`.
- `electron_count() -> u8`: returns total (via `i16`, cast to `u8`).
- `is_resolved() -> bool`: all contributions have `Some` electrons.
- `contains_atom()`, `atom_count()`, `all_atoms()` as before.

### 9.3 MulticenterBondBuilder

Enables staged construction of `MulticenterBond`:

```rust
struct MulticenterBondBuilder {
    sets: SmallVec<[MulticenterSet; 4]>,  // populated at topology (atoms only, electrons=None)
}
```

- `MulticenterBondBuilder::from_table_ir(table_mc, index_map)`: topology-only construction.
  Converts table_ir sets to graph_ir sets, remapping u32 → AtomIndex. electrons = None.
- `resolve_contributions(...)`: populate per-atom electron data (valence phase).
- `build() -> Result<MulticenterBond, ResolutionError>`: succeeds if either fully resolved or
  if strict multicenter validation is disabled (topology-only multicenter bonds are accepted).

### 9.4 Resolver changes

- `resolve_topology_with`: convert table_ir `MulticenterBond` to `MulticenterBondBuilder`:
  - Preserve set structure (center set, ligand sets) from table_ir.
  - Remap atom indices (u32 → AtomIndex).
  - All electrons = None at this stage.
- `resolve_valence_with`: populate per-atom electron contributions on each `MulticenterBondBuilder`.
  - Uses atom valence patterns (element type, charge, bond connectivity) as data inputs —
    not substructure heuristics.
  - When data is insufficient, contributions remain None; the bond is topology-only.
  - Graph symmetry (automorphism orbits, see section 9.6) can constrain equivalent atoms
    to have identical contributions.
- `MoleculeBuilder.build()`:
  - Strict mode: fails if any multicenter bond is unresolved.
  - Lenient mode: accepts topology-only multicenter bonds (electrons = None → 0).

### 9.6 Graph symmetry as a resolution constraint

The automorphism group of the molecular graph (computed during topology phase) provides orbit
information: which atoms are equivalent under graph symmetry. This constrains multicenter bond
resolution — atoms in the same orbit must have identical per-atom contributions.

Example: In ferrocene Cp ring, all 5 C atoms are in the same orbit, so each must contribute the
same number of electrons. Combined with element-type data (C in π system → 1e), this determines
all contributions without heuristics.

Similarly, in B₂H₆, the two bridging H atoms are equivalent (same orbit), so they must have
identical contributions.

Graph symmetry is available from the topology pass. It can be computed using nauty/Traces (see
section 9.7) and used as an optional constraint during valence resolution. Broken-symmetry
solutions (where the chemistry breaks the graph-theoretic symmetry) can be handled by making
this constraint configurable.

### 9.7 Graph automorphism detection

**Available Rust crates** (all based on nauty/Traces via `nauty-Traces-sys` FFI bindings):

| Crate | Version | API level | Key features |
|---|---|---|---|
| `nauty-Traces-sys` | 0.7.0 | Raw FFI | Direct access to `orbits` array, group generators. Most control, most boilerplate. |
| `nauty-pet` | 0.14.1 | High-level | petgraph integration, `AutomGroup` (full group enumeration), `AutomStats` (group size, orbit count), `CanonGraph` (canonical form). Supports node/edge weights. |
| `graph-canon` | 0.1.4 | Mid-level | petgraph integration, `CanonLabeling` (hashable), `AutoGroups` (group + size). Faster than nauty-pet, more barebones. |

**What we need**:

1. **Orbit partition** (which atoms are equivalent): this is the primary output for constraining
   multicenter bond resolution and detecting equivalent stereocenters. Nauty computes this as a
   byproduct of canonical labeling — the raw `orbits[v]` array gives the canonical representative
   of each vertex's orbit.
2. **Canonical labeling**: needed later for canonical SMILES output.
3. **Colored graphs**: we need element type, charge, bond order etc. as vertex/edge colors so
   that automorphisms respect chemical identity. All three crates support node/edge weights.

**Recommendation**: `nauty-pet` is the most mature option and provides the broadest API. However,
it does not directly expose the orbit partition (only `num_orbits` via `AutomStats`). The orbit
array is available from raw `nauty-Traces-sys`. A thin wrapper over `nauty-Traces-sys` that
extracts the orbit partition for a petgraph `StableGraph` may be the most practical approach.
Consider wrapping into a `graph_ir::symmetry` module.

**Concern**: nauty is C code with a C build system. The `nauty-Traces-sys` crate bundles it and
handles the build, but this adds a C compilation dependency. This is acceptable for a library
with scientific computing goals.

Invariants:

- inv o: (spin) orbital count invariant^8
  ```
  total e = unpaired e + 2 * lone pairs + 2 * donated pairs + 2 * accepted pairs + 2 * implicit H + 2 * valence + aromatic valence + I(aromatic valence) + multicenter valence
  ```
- inv e: electron count invariant
  ```
  total e = neutral e - charge + implicit H + valence + I(aromatic valence) + multicenter valence + 2 * accepted pairs
  ```
- inv q: total charge invariant
  ```
  total charge = sum(atom_i) charge_i + mol charge
  ```

^2 Valence = bond sum, does not include implicit Hs, donated pairs (dative bonds), or the following valence types, ar v = aromatic valence, mc v = multicenter valence
^3 Spin multiplicities: s = singlet, t = triplet, q = quartet
^4 Lone pairs do not include donated pairs
^5 Inv o: orbital count invariant, inv e: electron count invariant
^6 Charge-separated structure (R3N^+-O^-)
^7 Dative structure (R3N->O)

## 11. Scope and additional decisions

- **Multi-fragment**: No explicit multi-fragment structures in GraphIR. Topology validation is more relevant for CTab than SMILES (where `.` makes components explicit).
- **GraphIR types**: Like TableIR, expect (at least) 4 types: `Molecule`, `ExtendedMolecule` (later QueryMolecule, VariableMolecule — out of scope). **Initial scope**: `resolve_molecule(molecule: table_ir::Molecule) -> Result<graph_ir::Molecule, ResolutionError>` only. Others (resolve_reaction, resolve_extended_molecule, etc.) later. Share low-level functions.
- **Resolution vs. lint**: Separate configs. Resolution = hard errors; lint = additional checks on already-resolved GraphIR.
