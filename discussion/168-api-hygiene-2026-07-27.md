# Crate boundaries and API hygiene

Status: **Proposed**
Date: 2026-07-27
Relates: [105](105-dsl-fixes-2026-06-06.md),
[129](129-crate-organization-2026-06-24.md),
[130](130-crate-reorganization-plan-2026-06-24.md)

## Scope

This document tracks repository-wide API hygiene that is not owned by one
semantic subsystem. It replaces the corresponding mixed items in doc 105.

## Crate boundaries

- Review whether the DSL remains a module of `umol-ast` or should become an
  `umol-dsl` crate. Base the decision on dependency direction, compile-time
  coupling, and whether AST-only consumers can avoid the parser surface.
- Review domain-specific module sealing. A sealed internal module may expose
  its intended API at the crate root, but sealing is not a reason to obscure
  ordinary public types or methods.
- Keep external-format types in `umol-io`; do not move TableIR or format
  parsers into the semantic AST crates to simplify imports.

## Visibility

Audit `pub(crate)` and `pub(super)` declarations:

- make a symbol public when it is a coherent supported operation;
- make it private when it is an implementation detail used within one module;
- restructure modules when restricted visibility is compensating for an
  arbitrary file boundary;
- retain restricted visibility for sealed implementation traits and genuinely
  crate-internal coordination.

The goal is not maximal public visibility. It is to avoid a parallel
crate-private API that external consumers cannot use and maintainers must still
support.

## Re-exports

- Re-export a dependency's type only when it is part of this crate's public
  operation signature or vocabulary.
- Avoid wildcard and convenience re-exports that create multiple canonical
  import paths.
- Modules whose declared role is re-export organization contain no
  implementation.
- Preserve algorithmic transparency when a higher-level crate re-exports an
  algorithm selector.

## Basic trait coverage

Inventory public types across the workspace and determine which require the
conventional `FromStr`, `Display`, `PartialEq`, `Eq`, `Hash`, `PartialOrd`, and
`Ord` implementations. Add missing implementations where the semantics are
well defined and record intentional omissions. In particular:

- use `Display` for stable user-facing diagnostics rather than exposing
  `Debug` representations;
- implement `FromStr` only for types with an established textual input
  language;
- keep equality and hashing semantics consistent;
- add partial or total ordering only where the corresponding semantic order is
  defined.

## Public data-type contracts

Audit public data types and the operations that construct, convert, validate, and consume them
against the construction and provenance principles in
[doc 188](188-developer-guide-2026-08-05.md). Include internal carrier types when their contract is
relied upon by a public operation; do not limit the review to types already known to have a defect.

For each type:

- identify its intrinsic representation invariant and require every public constructor to establish
  that invariant;
- keep contextual coherence with an independently supplied graph, molecule, id space, model, or
  operation history out of constructors that do not receive that context;
- distinguish open data carriers from operation-issued, provenance-bound values, and require public
  consumers of open carriers to establish the contextual properties needed for their promised
  result;
- keep semantic validation lazy unless the operation being performed requires the semantic property;
- keep canonicalization, repair, stripping, resolution, and other transformations explicit rather
  than embedding them in construction or conversion;
- identify the first public operation that genuinely requires each property and place fallibility
  there rather than propagating it through unrelated callers;
- review whether absence, an operation-specific error, or an asserted producer contract best
  expresses each failure, while avoiding a proliferation of overlapping `Option` and `Result` forms;
- verify that asserted internal paths have a documented producer invariant and that externally
  reachable mismatches cannot become indexing panics.

Record corrections in the semantic subsystem's owning worklist rather than accumulating an
unstructured implementation plan here. The audit report should list intentionally infallible public
constructors and consumers as well as changes, so absence from the change list is not mistaken for
having been overlooked.

## Errors and diagnostics

Review the remaining error enums after the validator, IO, and transaction
work:

- empty error enums on implemented operations must disappear;
- errors identify the operation and failed precondition;
- model conversion, Rust/Python conversion, parsing, and invalid semantic
  structure remain distinct categories;
- errors should be composable without exposing implementation-only phases.
- aromaticity model-rejection diagnostics should identify the offending entities and distinguish
  causes such as element scope and ring size when that additional detail is useful.

Format-specific parsing errors and source spans are tracked in docs 153 and
164. Release-facing Python exception mapping remains in doc 163.

### Paired asserted and checked construction

When one source representation has both an asserted construction path for
already-established values and a checked path for runtime input, use paired
inherent names:

```rust
T::from_x(value)
T::try_from_x(value)
```

The checked name should retain the source representation instead of replacing
it with a generic `TryFrom` implementation unless generic conversion is an
actual consumer requirement. Do not expose both forms of the same checked
operation.

Apply this rule to `Permutation`: retain the asserted
`Permutation::from_image`, replace `TryFrom<&[usize]>` with
`Permutation::try_from_image`, and migrate parsing, Python conversion,
property strategies, tests, and other runtime-data callers. The ordinary fixed
and algorithm-produced image paths remain on `from_image`. Doc 185 applies the
same convention to molecule and reaction-span entries.

### Correspondence consumer preconditions

After the checked `Correspondence` construction work in
[doc 185](185-python-reaction-span-2026-08-04.md), audit public operations that
consume `Correspondence`, `GraphCorrespondence`, or
`MoleculeCorrespondence`. A correspondence may satisfy its own partial-
bijection invariant while declaring id-space sizes that do not agree with the
graph or molecule supplied to an operation.

- Inventory the public consumers in `umol-graph-core` and `umol-ast`, including
  induced correspondence construction, extraction, superimposition, and
  molecule differencing.
- Separate correspondence construction validity from contextual coherence
  with the supplied graph or molecule. Aggregating constructors do not become
  fallible when they have no contextual object against which to validate.
- Replace externally reachable indexing panics with explicit fallibility where
  callers may supply a structurally valid but contextually incompatible
  correspondence; settle `Option` versus an operation-specific error in the
  coordinated error review.
- Keep algorithm-produced correspondences on asserted paths when the producer
  establishes the required dimensions and incidence. State and check those
  producer contracts rather than exposing impossible algorithm-internal
  failures as ordinary results.
- Add exact unit and property coverage for dimension mismatches, valid induced
  correspondences, and preservation of the established infallible algorithm
  paths.

Doc 185 owns the correspondence defects already identified while defining the reaction-span bridge:
intrinsic error separation, directional totality, remapping, graph and molecule induction,
superimposition, and molecule differencing. This section retains the repository-wide inventory so
other consumers are checked under the same rule and the provisional `Option` surfaces can be
revisited coherently during the error review.

## Serialization dependencies

Audit every direct `serde` dependency and every `Serialize` / `Deserialize` implementation. Domain
types should not acquire an implicit persistence contract merely because deriving the traits is
convenient; persistent formats use an explicit boundary representation with defined semantics.

The current inventory gives the audit concrete starting points:

- Retain `umol-edn`'s optional `serde` feature and the tests and benchmarks that exercise it. Serde
  interoperability is an explicit capability of that boundary crate.
- Review the production serde surface in `umol-chem`. `Element`, isotope types, time types, and spin
  types derive or implement serde, but the repository callers found by the initial inventory are
  tests in that crate. `serde_json` is likewise used only by those tests, and the `serde` feature on
  `bitvec` has no identified consumer. Remove these production dependencies and trait impls unless a
  supported external representation is identified; do not preserve them solely as speculative
  convenience.
- Retain serde where it implements an actual input boundary, currently
  `ValenceTable::from_toml_str` in `umol-graph`. Keep the private deserialization helper separate from
  the semantic `ValenceTable` and `ValenceEntry` types.
- Confirm that the direct serde dependencies in `umol-graph-core`, `umol-io`, and `umol-geometric`
  remain dev-only support for fixture input or snapshot output. Test data formats do not establish a
  serialization contract for the corresponding public domain types.

After removals, regenerate the dependency graph and verify that no crate retains a direct serde or
serde-json dependency without a source-level consumer and an identified boundary or test role. This
is repository dependency and public-trait hygiene; changes to the `umol-edn` serde implementation or
the native DSL grammar remain in doc 164.

## Intermediate representations

Provide deliberate diagnostic formatting for TableIR, resolved stages, and
other intermediate representations where it helps inspect a pipeline. Debug
output is not a serialization contract. Any persistent interchange format
requires its own boundary type and versioned semantics.

## Completion criteria

- Each public symbol has one canonical import path.
- Restricted visibility corresponds to a real encapsulation boundary.
- Crate boundaries follow model ownership rather than import convenience.
- Every direct serialization dependency has an identified boundary or test role; semantic types do
  not carry accidental persistence contracts.
- Error categories follow public operations and do not expose internal
  implementation history.
