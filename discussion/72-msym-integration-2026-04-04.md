# libmsym integration: API design

## Status: draft (revised after design discussion)

## Design principles

1. **Semantics first, implementation second.** The public API models the domain (point groups, molecular symmetry, symmetry-adapted bases). The C library is an implementation detail hidden behind the API boundary.
2. **Every molecule has symmetry.** C1 is the trivial case, not the absence of symmetry. There is no separate "symmetric molecule" type.
3. **Molecules are immutable.** Transformations (symmetrization, perception) produce new molecules.
4. **PointGroup is a singleton.** There is exactly one C2v. Point groups are lazily constructed and stored as `&'static PointGroup`. Common groups have named constructors (`PointGroup::c2v()`). Arbitrary groups via `PointGroup::from_schoenflies("C7v")` use a dynamic registry. `Vec<Molecule>` with mixed symmetries works — `&'static` is `Copy`.
5. **Irreps are bound to their group.** An `Irrep` holds `&'static PointGroup`, preventing accidental misuse across groups. Group identity is pointer equality (`std::ptr::eq`).
6. **Heavy computations (SALCs, projectors) are methods that return owned results.** The molecule stores the cheap ingredients (equivalence sets, atom permutations). Expensive derived data is computed on demand, owned by the caller.

## Domain model

Three distinct concepts:

### 1. PointGroup — singleton algebraic object

One C2v exists, as a `&'static PointGroup`. It has no knowledge of any molecule.

```rust
struct PointGroup {
    label: SchoenfliesLabel,      // e.g. Cnv(2) for C2v
    order: usize,                // number of group elements
    operations: Vec<SymmetryOp>,
    character_table: CharacterTable,
}
```

Contains: symmetry operations (group elements) with 3×3 matrices, character table, irreps, class structure. Can answer purely algebraic questions: direct products, selection rules, subgroup relationships.

Point groups are lazily constructed via libmsym and cached as `&'static`. Common groups have named constructors generated by macro:

```rust
macro_rules! point_group_fn {
    ($name:ident, $schoenflies:expr) => {
        pub fn $name() -> &'static PointGroup {
            static PG: LazyLock<PointGroup> =
                LazyLock::new(|| PointGroup::construct($schoenflies).unwrap());
            &PG
        }
    };
}

impl PointGroup {
    point_group_fn!(c1, "C1");
    point_group_fn!(c2, "C2");
    point_group_fn!(cs, "Cs");
    point_group_fn!(ci, "Ci");
    point_group_fn!(c2v, "C2v");
    point_group_fn!(c2h, "C2h");
    point_group_fn!(c3v, "C3v");
    point_group_fn!(d2h, "D2h");
    point_group_fn!(d3h, "D3h");
    point_group_fn!(td, "Td");
    point_group_fn!(oh, "Oh");
    point_group_fn!(ih, "Ih");
    // ... etc for common groups

    /// Arbitrary group by Schoenflies symbol. Uses dynamic registry.
    fn from_schoenflies(name: &str) -> Result<&'static PointGroup, Error>;
}
```

For C1: one operation (identity), one irrep (A), trivial character table.

### 2. Molecule — always carries symmetry data

```rust
struct Molecule {
    elements: Vec<Element>,
    coords: Coordinates,
    charge: i32,
    multiplicity: SpinMultiplicity,

    // Symmetry data — always present, trivial for C1
    group: &'static PointGroup,
    equivalence_sets: Vec<Vec<usize>>,  // atom index orbits
    atom_permutations: Vec<Vec<usize>>, // one per operation
    orientation: Orientation,            // transform to standard orientation
}
```

A freshly constructed molecule from Cartesian coordinates gets `PointGroup::c1()` with identity permutations and singleton equivalence sets (one per atom). This is cheap: a `&'static` reference and a few small `Vec<usize>`.

Perception produces a new `Molecule` with the discovered group and associated data:
```rust
impl Molecule {
    fn perceive_symmetry(&self, thresholds: &Thresholds) -> Result<Molecule, Error>;
    fn symmetrize(&self, thresholds: &Thresholds) -> Result<Molecule, Error>;
}
```

Both return new `Molecule` values. `perceive_symmetry` discovers the group and populates equivalence sets / permutations. `symmetrize` additionally snaps coordinates to exact symmetry.

### 3. Symmetry-adapted bases — computed on demand

A symmetry basis is a representation of the point group on a vector space derived from the molecule. The molecule stores the raw ingredients; the analysis is a method that returns an owned result.

```rust
impl Molecule {
    /// SALCs of arbitrary basis functions via libmsym.
    fn salc_basis(&self, basis: &[BasisFunction]) -> Result<SalcBasis, Error>;

    /// Symmetry-adapted displacement coordinates: Γ_3N → Γ_trans + Γ_rot + Γ_vib.
    /// Pure Rust, using atom_permutations + character table.
    fn symmetry_coordinates(&self, weighting: MassWeighting) -> SymmetryCoordinates;
}
```

The caller owns the result. If they need it multiple times, they hold onto it. The molecule is not burdened with cached derived data.

## PointGroup type

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub enum SchoenfliesLabel {
    // Finite groups — rotational parameter encoded on variant
    Ci,
    Cs,
    Cn(u32),
    Cnh(u32),
    Cnv(u32),
    Sn(u32),   // n even, n >= 4
    Dn(u32),
    Dnh(u32),
    Dnd(u32),
    T, Td, Th,
    O, Oh,
    I, Ih,
    // Continuous groups — no finite character table, SALC machinery is different
    Coov,   // C∞v (HCl, CO)
    Dooh,   // D∞h (CO2, N2)
    K,      // full rotation group
    Kh,     // full rotation + inversion (single atom)
}

#[derive(Debug)]
pub struct PointGroup {
    label: SchoenfliesLabel,
    order: usize,               // finite groups only; 0 for continuous
    operations: Vec<SymmetryOp>, // finite groups only; empty for continuous
    character_table: CharacterTable, // finite groups only
}

impl PointGroup {
    pub fn name(&self) -> String;       // derived from label
    pub fn label(&self) -> SchoenfliesLabel;
}
```

Not `Clone` or `Copy` — point groups are singletons accessed via `&'static`. Equality is pointer equality (`std::ptr::eq`). The Schoenflies name is derived from the label, not stored.

`SchoenfliesLabel` is `Copy` — it's the structured Schoenflies symbol. Invalid labels (e.g. `Sn(3)`, `Cn(0)`) are rejected at construction.

Construction is shown above in the domain model section (macro-generated named constructors + `from_schoenflies` with dynamic registry).

### SymmetryOp type

```rust
struct SymmetryOp {
    kind: SymmetryOpKind,  // Identity, ProperRotation, ImproperRotation, Reflection, Inversion
    order: i32,
    power: i32,
    orientation: SymmetryOpOrientation,  // None, Horizontal, Vertical, Dihedral
    vector: [f64; 3],             // axis or plane normal
    class: i32,                   // index into character table classes
    matrix: Matrix3<f64>,         // the 3×3 transformation matrix
}
```

Note: the 3×3 matrix is stored on the operation. libmsym provides axis + type + order; the matrix is derived from those. Having it pre-computed avoids reconstructing it every time we build representation matrices.

### CharacterTable and Irrep

`CharacterTable` stores irrep data internally. `Irrep` is a user-facing view that borrows from the `'static` point group, carrying a back-reference to prevent cross-group misuse.

```rust
// Internal storage (inside CharacterTable, inside PointGroup)
struct IrrepData {
    name: String,
    dimension: i32,
    characters: Vec<f64>,   // one per conjugacy class
}

struct CharacterTable {
    irrep_data: Vec<IrrepData>,
    class_sizes: Vec<i32>,
    class_operations: Vec<SymmetryOp>,  // one representative per class
    order: usize,
}

// User-facing handle — borrows from &'static PointGroup
#[derive(Copy, Clone)]
struct Irrep {
    data: &'static IrrepData,
    group: &'static PointGroup,
}

impl Irrep {
    fn name(&self) -> &str;
    fn dimension(&self) -> i32;
    fn characters(&self) -> &[f64];
}
```

`Irrep` is `Copy` (two `&'static` references). Characters live on the irrep, not in a separate 2D array on the table — each `IrrepData` owns its character row.

All algebraic methods live on `PointGroup`, not `CharacterTable`. The user never touches `CharacterTable` directly.

```rust
impl PointGroup {
    fn irreps(&'static self) -> Vec<Irrep>;
    fn irrep(&'static self, name: &str) -> Option<Irrep>;
    fn direct_product(&'static self, a: Irrep, b: Irrep) -> Vec<(Irrep, u32)>;
    fn contains_totally_symmetric(&'static self, a: Irrep, b: Irrep, c: Irrep) -> bool;
    fn reduce(&'static self, characters: &[f64]) -> Vec<(Irrep, u32)>;
    fn translation_irreps(&'static self) -> Vec<(Irrep, u32)>;
    fn rotation_irreps(&'static self) -> Vec<(Irrep, u32)>;
}
```

`translation_irreps` and `rotation_irreps` are computed from the 3×3 matrix characters of the operations (trace of Cn = 1 + 2cos(2π/n), etc.) and their symmetric/antisymmetric parts. No external data needed, but Katzer tables serve as validation.

## Molecule construction and perception

```rust
impl Molecule {
    /// From Cartesian coordinates. Symmetry defaults to C1.
    fn from_cartesian_angstrom(
        elements: Vec<Element>,
        coords: &[f64],
        charge: i32,
        spin: SpinMultiplicity,
    ) -> Self;

    /// Detect point group symmetry. Returns a new molecule with the
    /// discovered group, equivalence sets, atom permutations, and
    /// standard orientation.
    fn perceive_symmetry(&self, thresholds: &Thresholds) -> Result<Molecule, Error>;

    /// Symmetrize: perceive + snap coordinates to exact symmetry.
    /// Returns a new molecule with exact symmetry.
    fn symmetrize(&self, thresholds: &Thresholds) -> Result<Molecule, Error>;

    /// Generate full molecule from asymmetric unit + group.
    fn symmetrize_to(
        label: SchoenfliesLabel,
        elements: Vec<Element>,
        coords: &[f64],
    ) -> Result<Molecule, Error>;
}
```

Internally, `perceive_symmetry` and `symmetrize`:
1. Create a transient libmsym context (not exposed)
2. Set atoms, call `msymFindSymmetry` (and `msymSymmetrizeElements` for symmetrize)
3. Extract: group, operations, character table, equivalence sets
4. Compute atom permutations (see open question below)
5. Construct and return the new `Molecule`
6. Drop the C context

## Displacement analysis (pure Rust)
```rust
struct SymmetryCoordinates {
    basis_functions: Vec<BasisFunction>,  // 3N displacement basis
    gamma_total: Vec<(Irrep, u32)>,
    gamma_trans: Vec<(Irrep, u32)>,
    gamma_rot: Vec<(Irrep, u32)>,
    gamma_vib: Vec<(Irrep, u32)>,
    coordinates: Vec<IrrepCoordinates>,   // each classified by CoordinateKind
    weighting: MassWeighting,
}

impl Molecule {
    fn symmetry_coordinates(&self, weighting: MassWeighting) -> SymmetryCoordinates;
}
```

Algorithm:

1. **Build 3N×3N representation matrices** for each operation, using `atom_permutations` and the 3×3 operation matrices stored on `SymmetryOp`.
2. **Compute Γ_3N characters**: χ(R) = Σ_{atoms fixed by R} tr(3×3 matrix of R). Only atoms mapped to themselves contribute.
3. **Reduce Γ_3N** via `PointGroup::reduce`.
4. **Identify Γ_trans and Γ_rot** via `PointGroup::translation_irreps()` and `rotation_irreps()`.
5. **Subtract** to get Γ_vib.
6. **Project** via P_μ = (l_μ/h) Σ_R χ_μ(R)* · D_3N(R) applied to trial vectors. Orthogonalize within each irrep subspace (SVD). Classify each resulting coordinate as translation, rotation, or vibration.

Steps 1-5 use only characters (cheap). Step 6 needs the full 3N×3N matrices (allocated transiently). nalgebra handles all linear algebra.

Mass-weighting: the projection in step 6 can use mass-weighted coordinates (for normal mode analysis) or unweighted (for symmetry classification). Both are useful; the method should accept an option.

## Selection rules

Methods on `PointGroup`, not on `Molecule`, because these are purely algebraic:

```rust
impl PointGroup {
    /// Electric dipole allowed? Checks Γ_i ⊗ Γ(x,y,z) ⊗ Γ_f ⊃ A1.
    fn electric_dipole_allowed(&'static self, initial: Irrep, final_: Irrep) -> bool;

    /// Electric quadrupole allowed?
    fn electric_quadrupole_allowed(&'static self, initial: Irrep, final_: Irrep) -> bool;

    /// Raman allowed? Checks against irreps of (x², y², z², xy, xz, yz).
    fn raman_allowed(&'static self, initial: Irrep, final_: Irrep) -> bool;

    /// Magnetic dipole allowed? Checks against irreps of (Rx, Ry, Rz).
    fn magnetic_dipole_allowed(&'static self, initial: Irrep, final_: Irrep) -> bool;
}
```

Convenience methods on `SymmetryCoordinates`:

```rust
impl SymmetryCoordinates {
    /// Which vibrational irreps are IR-active?
    fn ir_active(&self) -> Vec<Irrep>;

    /// Which vibrational irreps are Raman-active?
    fn raman_active(&self) -> Vec<Irrep>;
}
```

These don't need an explicit `CharacterTable` parameter — the `Irrep`s in `SymmetryCoordinates` already carry their group reference.

## Symmetry-adapted basis types

### BasisKind — what kind of functions are being symmetry-adapted

```rust
enum BasisKind {
    /// s-type: atoms themselves (permutation representation). l=0.
    Atom,
    /// p-type: Cartesian displacement on an atom. l=1.
    Displacement(CartesianAxis),
    /// Real spherical harmonic Y_l^m centered on an atom.
    RealSphericalHarmonic,
    /// Cartesian multinomial x^i y^j z^k with i+j+k=l centered on an atom.
    /// 6 functions for l=2 (vs 5 RSH), 10 for l=3 (vs 7), etc.
    Cartesian,
}

enum CartesianAxis { X, Y, Z }
```

### BasisFunction — a concrete basis function on a specific atom

Input to libmsym and label for SALC coefficients.

```rust
struct BasisFunction {
    atom_index: usize,
    kind: BasisKind,
    n: i32,    // counting index (distinguishes shells, not a physical QN)
    l: i32,
    m: i32,
}
```

For `Atom`: l=0, m=0, n=0. For `Displacement(X)`: l=1, m=1, n=0 (axis encoded as m).
For RSH/Cartesian: l and m as given, n distinguishes e.g. 2s from 3s.

### Salc — one symmetry-adapted linear combination

A linear combination of basis functions, indexed into the basis set.

```rust
struct Salc {
    coefficients: Vec<(usize, f64)>,  // (basis_function_index, coefficient)
}
```

Sparse representation — only non-zero terms stored. The basis function ordering
is defined by the parent `SalcBasis` or `SymmetryCoordinates`.

### IrrepBasis — SALCs for one irrep

```rust
struct IrrepBasis {
    irrep: Irrep,
    salcs: Vec<Salc>,
}
```

### SalcBasis — symmetry-adapted basis across all irreps

The general result type for orbital SALCs and atom permutation SALCs.

```rust
struct SalcBasis {
    basis_functions: Vec<BasisFunction>,
    irreps: Vec<IrrepBasis>,
}
```

### Displacement-specific types

Displacement SALCs carry additional physical metadata (coordinate classification,
mass-weighting) that doesn't apply to orbital or atom SALCs.

```rust
enum CoordinateKind {
    Translation,
    Rotation,
    Vibration,
}

enum MassWeighting {
    Unweighted,
    MassWeighted,
}

struct IrrepCoordinates {
    irrep: Irrep,
    kind: CoordinateKind,
    salcs: Vec<Salc>,
}

struct SymmetryCoordinates {
    basis_functions: Vec<BasisFunction>,  // 3N displacement basis, ordered
    gamma_total: Vec<(Irrep, u32)>,
    gamma_trans: Vec<(Irrep, u32)>,
    gamma_rot: Vec<(Irrep, u32)>,
    gamma_vib: Vec<(Irrep, u32)>,
    coordinates: Vec<IrrepCoordinates>,
    weighting: MassWeighting,
}
```

## Crate structure and dependencies

```
umol-geometric
  ├── umol-data       (Element, atomic masses, units)
  └── umol-msym       (PointGroup, Irrep, perception/symmetrization impl)
        └── umol-msym-sys
              └── libmsym (C, git submodule)
```

- `umol-msym` depends on `umol-data` (needs `Element` for mass lookup in conversions to libmsym atoms).
- `umol-geometric` depends on `umol-msym` (needs `PointGroup`, `Irrep`, `SchoenfliesLabel`, etc. as fields and return types).
- The `Molecule` methods (`perceive_symmetry`, `displacement_analysis`, etc.) live in `umol-geometric` since `Molecule` is defined there.
- `umol-msym` provides: `PointGroup`, `SchoenfliesLabel`, `Irrep`, `SymmetryOp`, `Thresholds`, `Error`, and the internal `Context`/`CharacterTable` wrappers (not public).
- `umol-msym` does NOT depend on `umol-geometric`. No circular dependency.

## Open questions

1. ~~**Atom permutations.**~~ **Resolved.** Computed in Rust. For each operation, apply the 3×3 matrix to each atom position, find the nearest atom within threshold. libmsym computes this internally (`findPermutation` in `permutation.c`) but stores it per-equivalence-set and does not expose it through the public API. Our Rust implementation produces global permutations (atom i → atom j across the whole molecule), which is the format we need for building 3N×3N representation matrices. The algorithm is O(N²) per operation — negligible for molecular sizes.

2. ~~**Katzer data as test oracle.**~~ **Resolved.** Automated comparison implemented in `umol-msym/tests/katzer_comparison.rs`. 18 tests cover C2, Cs, Ci, C2v, C2h, D2d, D2h, C3, C6, S4, D2, T, Th, Td, O, Oh, I, Ih. Character tables from libmsym match Katzer data (comparison is order-independent via character fingerprints, handles different class orderings and irrep naming conventions). Irrational characters (Ih golden ratio) match to 3 decimal places.

3. ~~**Mass-weighting in displacement analysis.**~~ **Resolved.** Enum parameter `MassWeighting` on `symmetry_coordinates()`, saved on the `SymmetryCoordinates` result type so downstream code knows what it's working with.

4. ~~**PointGroup construction without molecules.**~~ **Resolved.** All point groups treated uniformly via libmsym — `PointGroup::from_schoenflies("C7v")` works the same as `from_schoenflies("C2v")`. No special-casing for crystallographic groups. libmsym handles arbitrary n.

5. ~~**Coordinates variant.**~~ **Resolved.** The `Symmetric` variant is removed from the `Coordinates` enum. The enum itself stays — it distinguishes coordinate types (Cartesian, internal, redundant internal, etc.), which is a separate concern. The `Symmetric` variant was orthogonal to that distinction and is no longer needed because: (a) every molecule now carries its `PointGroup` + equivalence sets + permutations, (b) the asymmetric unit is a derived view (one representative per equivalence set), (c) symmetry-adapted coordinates are produced on demand by `symmetry_coordinates()`, which returns both SALC definitions and evaluated values.

6. ~~**Irrep identity across groups.**~~ **Resolved.** Irreps are structurally bound to their point group. An `Irrep` holds `&'static PointGroup`, making it impossible to outlive its group and enabling `std::ptr::eq` checks to prevent cross-group misuse. This requires PointGroup to be a singleton (`&'static`), which is the mathematically correct model — there is exactly one C2v. Implemented via `LazyLock` for named constructors and a dynamic registry for arbitrary n. `CharacterTable` becomes an internal detail; all algebraic methods (direct products, reduction, selection rules) move to `PointGroup`.
