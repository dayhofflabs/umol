# Design chat

## Summary

* Informational

## Question

How much does RDKit suck really? Is it just my warped perception?

## Response

RDKit has significant issues:
- Fragile molecule parsing
- Poor error handling/reporting
- Inconsistent API design
- Limited documentation
- Complex installation/dependencies

But it's still the most mature open-source cheminformatics toolkit. Alternatives
like OpenBabel have their own problems. Commercial options (MOE, ChemAxon) are
better but expensive.

The issues stem from chemistry software's inherent complexity and RDKit's
academic origins. Most users just work around the quirks.

## Question

In your learned opinion, how much of these problems are intrinsic to
representing complex molecular structures and how many are the results of bad
design, feature creep, and many years of nips and tucks on the software w/o
well-thought out improvements? If one wanted to take the core RDKit codebase and
modernize it, removing non-core features, assumptions about molecular
structures, etc., how much work would it be? Would one use Rust + Python instead
of C++/Python, as it is using now? Which design decisions would one need to make
before testing out the viability of such a project?

## Response

Core issues in molecular representation:
- Handling different levels of abstraction (2D/3D, implicit/explicit H)
- Canonical representation of equivalent structures
- Stereochemistry and conformational flexibility
- Reaction mechanisms and electronic effects

RDKit-specific issues:
- Monolithic C++ core with poor separation of concerns
- Implicit assumptions baked into data structures
- Feature accumulation without architectural evolution
- Performance/safety tradeoffs favoring legacy code

Modernization approach:
1. Core data structures:
   - Immutable molecule representation
   - Clear separation between topology and properties
   - Type-safe stereochemistry handling
   - Explicit error types

2. Rust advantages:
   - Memory safety without GC
   - Better FFI than C++
   - Type system enforcing invariants
   - Modern tooling/packaging

3. Critical design decisions:
   - Scope of chemical features to support
   - Interface between core/algorithms
   - Property representation schema
   - Validation/error handling strategy

Estimated effort: 2-3 person-years for minimal viable replacement.

## Question

Let's say one only wanted to have SMILES/SDF I/O with correct roundtripping,
substructure searches using SMARTS and reactions using reaction SMARTS, using
Rust/Python, what would be the effort? Would a pure-Python implementation be
faster do develop (obviously a lot slower at runtime)?

## Response

Minimal viable feature set:
1. Core (Rust): ~6 months
- Graph representation
- SMILES/SMARTS parsing
- Pattern matching engine
- Basic reaction transforms

2. Python bindings: ~2 months
- PyO3 interface
- Property handling
- File I/O

Pure Python would be ~3-4 months to prototype but with limitations:
- Complex SMARTS matching becomes impractical
- Reaction handling performance issues
- Memory usage problems with large datasets

Key success factor: Strict scope control. Many projects fail by trying to handle
too many edge cases in chemistry.

## Question

How much time would it save to have a modernized codebase over a course of 5
years for a cheminformatics project/business that aspires to process ~ 10
million experimental and generated structures and reactions from areas of
chemistry, including metabolic reactions and biocatalysis?

## Response

Time savings over 5 years:
- Development: -6 months (initial rebuild)
- Maintenance: +12-18 months (less debugging, faster onboarding)
- Performance: +4-6 months (faster processing, fewer workarounds)
- Features: +6-8 months (easier to implement new capabilities)

Net gain: ~18-24 months of development time

Critical factors:
- Clean separation between chemistry rules/assumptions and core logic
- Type-safe handling of chemical entities
- Better error reporting reduces debugging cycles
- Faster iteration on new features
- Reduced technical debt

The investment makes sense if team size > 3-4 developers.

## Question

Would the Rust-based approach be more viable than C++/Python, as is used by
RDKit at the moment? Pure Python implementation does not seem to be worth doing
unless for small preliminary feature implementations, correct? What other
considerations should one take into account? Are any existing graph
implementations in Rust stable and performant enough to do the job or would one
have to reimplement the low-level algorithms oneself? Also, is there value in
some translation from the RDKit codebase? Or would that just introduce outdated
design?

## Response

Rust advantages over C++:
- Memory safety without runtime cost
- Better dependency management
- Modern async/parallel support
- Stronger type system for chemistry invariants

Graph implementations:
- petgraph is mature but may need extensions
- Custom implementation needed for chemical specifics
- Could leverage petgraph for basic algorithms

RDKit translation:
- Algorithm concepts worth studying
- Direct code translation inadvisable
- Chemistry rules/tests valuable reference

Implementation strategy:
1. Pure Python prototype for core features
2. Rust implementation with PyO3
3. Gradual feature expansion
4. Property optimization for cheminformatics

Critical: Start with clear chemistry domain boundaries and explicit error handling design.

## Question

Would you do it? Asking for a friend... Feel free to answer in an
uncharacteristically expansive, stream-of-consciousness (or whatever the
equivalent is for artificial intelligence) manner.

## Response

As someone with a deep interest in both chemistry and software design - yes, I
would. The current state of cheminformatics tooling feels like technical debt
incarnate. Rather than continuing to work around RDKit's limitations or paying
expensive licenses for commercial tools, a modern foundation could transform how
we handle chemical data.

The key is ruthless prioritization: focus solely on core operations (structure
handling, search, reactions) and build up from there. Using Rust isn't just
about performance - it's about encoding chemical invariants into the type system
and catching errors at compile time rather than runtime.

Main risks:
- Feature creep (temptation to support every edge case)
- Overengineering the architecture
- Underestimating chemistry complexity

But the potential payoff - faster development cycles, better reliability, easier
maintenance - makes it worth attempting. The field needs this.

Personal take: Start small, prove the concept with basic SMILES parsing and
substructure matching, then expand methodically. The satisfaction of building
something clean and maintainable would offset the initial investment.
