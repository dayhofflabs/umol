- Are the algorithms inherently streamable?

  Yes. All six algorithms can, in principle, emit matches incrementally. None needs the complete match set before it knows that an individual assignment is valid.

  - VF2: can emit whenever its recursive mapping becomes complete.
  - Ullmann: needs its candidate-matrix preprocessing, but completed backtracking assignments can then stream.
  - RI: can stream completed assignments after calculating its static query order.
  - ArcMatch: needs domain construction, consistency/path reduction, and variable ordering first; its subsequent backtracking results can stream.
  - VF2-RDKit: can stream completed mappings directly.
  - Ray–Kirsch: can stream completed bond mappings and isolated-atom assignments.

  Thus “lazy results” does not imply “no eager work.” Ullmann and especially ArcMatch retain substantial eager preprocessing, but they do not need eager result collection.

  The current implementations all pass a mutable results: Vec<_> down their recursive search and push at the solution leaf. For example, VF2 stores results in its search state in
  umol-graph-core/src/algorithms/subiso.rs:550.

  There are two materially different ways to change that:

  - A visitor/callback API is relatively straightforward:

    fn visit_subgraph_isomorphisms(
        ...,
        emit: impl FnMut(Correspondence<NodeId>) -> ControlFlow<()>,
    )

    Each solution leaf calls emit. This avoids result storage and supports early termination, limits, existence checks, and reaction application during enumeration.

  - A true Iterator::next() API is harder. The recursive search must become a resumable state machine with an explicit backtracking stack. Stable Rust cannot simply suspend an
    ordinary recursive function at yield and resume it later. Each algorithm would need cursor state capable of preserving its current mapping, candidate position, restoration
    information, and search depth.

  A callback is therefore the natural first graph-core streaming abstraction. But callbacks alone do not directly produce a Python generator: Python needs to suspend and resume
  between __next__ calls. For genuine Python-side search laziness, we eventually need either an explicit resumable search cursor or a less attractive producer-thread/channel adapter.

## Naming convention

  “Iterative” currently conflates two APIs:

  1. Streaming visitor: recursive search may remain recursive, but results are delivered individually.
  2. Resumable iterator: Iterator::next() suspends and resumes explicit search state.

  Use three distinct names:

  pub fn visit_cycles<B>(
      &self,
      ...,
      visitor: impl FnMut(Cycle) -> ControlFlow<B>,
  ) -> ControlFlow<B>;

  pub fn enumerate_cycles(
      &self,
      ...,
  ) -> Vec<Cycle>;

  pub fn iter_cycles(
      &self,
      ...,
  ) -> CycleIter<'_>;

  The contract is:

  - visit_*: callback streaming and early termination.
  - enumerate_*: eager collection of the complete result.
  - iter_*: actual resumable Rust iterator; result type uses the established Iter suffix.

  Not every operation needs all three. visit_* plus enumerate_* is sufficient until suspension across calls has a real consumer.

  ## Progressive conversion

  1. Convert one algorithm family internally from results.push(...) to an emitter callback.
  2. Keep its existing eager public method unchanged.
  3. Make that eager method collect the callback emissions.
  4. Expose visit_* only after every variant behind that algorithm selector obeys the streaming contract.
  5. Migrate consumers needing early termination or reduced memory.
  6. Add iter_* only when an explicit resumable cursor is justified.

  This keeps graph-core compiling at every point and avoids a temporary split where, for example, visit_subgraph_isomorphisms(Vf2) streams while another selector variant secretly
  materializes every result first.

  For an eventual true iterator, reverse the implementation layering:

  iter_*      owns the explicit search state
  visit_*     consumes iter_* until completion or Break
  enumerate_* collects iter_*

  Until then:

  visit_*     owns recursive search
  enumerate_* collects visit_*

  ## Simple-graph and multigraph execution paths

  Input-graph dispatch is independent of the `visit_*` / `enumerate_*` /
  `iter_*` result-delivery distinction. In particular, `simple` in
  `SimpleCycleEnumerationAlgorithm` describes the emitted cycles, not the
  input graph. Use *simple graph* and *multigraph* explicitly when discussing
  the input domains; do not call the latter “general cycle enumeration,” which
  could instead mean enumeration of closed walks with repeated vertices.

  The current Read--Tarjan and Vismara selectors each govern both input paths.
  Read--Tarjan's multigraph-capable path is edge-aware; Vismara's extracts
  loops and applies the same analysis through subdivision before projecting
  source identifiers back. These are domain-lifting paths for the selected
  algorithm, not independently selectable cycle-enumeration algorithms.
  Consequently, the total `visit_*_cycles` and `enumerate_*_cycles` operations
  take one selector and dispatch between direct simple-graph execution and the
  multigraph fallback. Their fallible `try_*` counterparts expose the strict
  simple-graph precondition, while the explicit `*_fallback` counterparts
  expose the multigraph path for validation and benchmarking (doc 158 S5e).

  Do not introduce separate simple-graph and multigraph selector enums merely
  to represent this dispatch. Split the selectors only if independently
  selectable multigraph algorithms are added. This differs from maximum
  matching: Hopcroft--Karp and Edmonds are genuinely distinct restricted and
  unrestricted algorithms, so
  `bipartite_maximum_matching_or_general` takes both selectors.
