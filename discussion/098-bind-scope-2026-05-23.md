# Bind scope on atoms (and possibly molecules)

Status: **Design discussion — open, relocated to the molecule level by doc 113.**

> **Update (113, 2026-06-16) — not superseded, relocated.** The 113 AST restructure
> removed *atom-level* `Bind`/`Ref` (a field variable is now a bare `Var(String)`
> occurrence). That moots the atom-local *mechanism* questions below (per-atom
> declaration registry, `AtomBindTarget`, inline ids, Q2–Q8) but does **not** dissolve
> the substance: **variable scope, cross-entity variable references, and storage**
> persist — now as **molecule-level** concerns (Q1's answer is "molecule," its *form*
> still open). The variable/constraint layer is designed at the molecule level later;
> nothing here became irrelevant.

## Why this came up

Doc 96 (valence-resolution plan) substep 2k specifies a DSL parser for the joint-domain constraint:

```
Fe#c+2#n?n#u?u#E(?n,?u) :: {(3,0), (1,4)}
```

The `?n`, `?u` here are *bind names*. They're declared on per-field predicates (`#n?n`, `#u?u`) and then referenced inside `#E(...)`. At the AST level, `JointDomainAst::Domain` stores `Vec<JointVar>` (an enum tag for atom fields) — no bind names at all. The parser is supposed to resolve `?n` → `JointVar::Charge` (or whatever), the formatter to invert it.

Trying to write that parser/formatter exposed a deeper issue: **the AST has no notion of "what variables this atom declares"**. Bind ids live inline on each field's `Bind/Ref` variant (`ValueAst::Bind(Box<(String, Vec<i64>)>)`, `ElementAst::Bind(Box<(String, MemOp, Vec<Element>)>)`, `IsotopeAst::Bind(Box<(String, MemOp, Vec<i64>)>)`). There is no central registry per atom. Several things are silently broken or undefined:

- Parser can't validate that `?n` in `#E(?n, ...)` is actually declared somewhere.
- Same id can be declared twice on different fields with conflicting targets — no enforcement.
- Programmatic construction can produce atoms with JD referencing undeclared binds; the inconsistency surfaces only when Display runs (with no recovery).
- Display can't render a JD whose vars don't have a bind/ref on the corresponding field — no `?id` to print.
- Doc 96 line ~977 already flagged "Bind-name scoping. Atom-local (atom-id-qualified) or molecule-scope (cross-atom referenceable)?" as an open question. It's not resolved.

The right fix is not patching Display or wrapping the parser in a try-resolve loop. It's introducing the **bind scope** as a first-class concept on the entity (atom, possibly molecule), with clear semantics, validation, and Lattice/Display behavior.

This doc lays out the design space, not a plan.

## What 2h gave us (don't touch)

`JointDomainAst` is complete and tested as of 2026-05-22:

- `enum JointDomainAst { Undetermined, Domain(DomainState) }` with private-fields struct payload.
- Constructor `from_ints(vars, tuples)` with all invariants (vars ≥ 1, tuples ≥ 1, arity, no dup vars).
- Full `Lattice` impl: relational meet (natural join — cartesian / equijoin / intersection), join with projection-to-shared-or-Undetermined, projection-rule matches, plus `is_undetermined` / `is_ground`.
- `project<F>` helper used by `saturate_atom` (2j).
- 39 unit tests covering the lattice ops.

`AtomConstraint::JointDomain(JointDomainAst)` is wired (2g), `saturate_atom` is wired (2j), the derive macro is wired (2i). All green.

What's *not* there: parser, formatter, EDN roundtrip. None of those will work principled-ly until the bind-scope question below is settled.

## The design space

Three orthogonal questions. Each has options. None is decided yet.

### Q1. Scope level

a. **Atom-local only.** Each `AtomAst` owns its own scope; ids live within one atom. Simplest; no cross-atom references.

b. **Molecule-wide only.** `MoleculeAst` owns the scope; an id refers to one (atom, field) pair anywhere in the molecule. Most general; matches existing `ElementAst::Ref` usage which is *already* cross-atom-capable today (despite nothing in the code validating it).

c. **Both — atom-local with molecule-wide promotion.** Atoms have local scopes; molecule has a derived view merging them, plus possibly its own top-level scope for cross-atom-only binds. Most general, also most complex.

**My read**: both views are natural; the bind scope itself does not commit either way. User's stated preference is "both," with atom-local first and molecule-wide as a derived view (or separately stored top-level table) for cross-atom relational uses such as sum-of-neighbour-charges. Pick the atom-local shape so it composes cleanly with a molecule-wide extension later.

### Q2. Representation

a. **Stored field** on `AtomAst`: `binds: BTreeMap<String, AtomBindTarget>`. Explicit, single source of truth for declarations. Needs sync with field `Bind/Ref` variants (since those also carry the id). Validation has to enforce consistency.

b. **Derived view.** `AtomAst::bind_scope() -> BindScope` walks fields and builds the map on demand. No stored field; source of truth stays on the field `Bind/Ref` variants. No sync issues; computed each call.

**Trade-offs**:

- (a) makes "what binds does this atom declare" cheap and explicit; downstream invariants reference it directly. Cost: every place that produces a `Bind` field must also update the registry; validation enforces this.
- (b) is zero-cost-at-construction but every consumer (Display, parser resolution, validation) rebuilds the map.
- (b) does not by itself solve duplicate-id collisions across fields — those are detected only when you try to look up an id that maps ambiguously.
- (a) makes the AST schema bigger; (b) keeps it as-is.

### Q3. Are bind ids one namespace or per-type?

a. **One namespace** across `ValueAst::Bind`, `ElementAst::Bind`, `IsotopeAst::Bind`. The id maps to a typed target (an `AtomBindTarget` enum that names which field). Collision (`#h?n` + `#i?n`) is an error.

b. **Per-type namespaces** — value-binds, element-binds, isotope-binds keep separate id spaces. Each reference site knows which namespace to consult. `#h?n` and `#i?n` can coexist.

**Trade-offs**:

- (a) matches Rust-style scoping (one name, one binding). Reads cleanly: `?n` always means one thing in scope.
- (b) is permissive but invites confusion: `#E(?n,...)` would need to disambiguate which `?n`. Probably bad for readability.

## What an `AtomBindTarget` would look like

If we go with (Q1=a or c, Q2=a, Q3=a), the type would be:

```rust
pub enum AtomBindTarget {
    // value-typed slots
    Charge, ImplicitHydrogens, LonePairs,
    UnpairedElectrons, Multiplicity,
    Valence, DonatedPairs, AcceptedPairs,
    // non-value-typed slots
    Element,
    Isotope,
}
```

The value-typed variants overlap with `JointVar`. Two options:

- **Fold `JointVar` into `AtomBindTarget`** — single source of truth for "field tags".
- **Keep them separate** — `JointVar` is constraint-internal (used inside `JointDomainAst`); `AtomBindTarget` is namespace-internal (used inside the bind registry). Provide `AtomBindTarget::as_joint_var() -> Option<JointVar>` for the JD path.

Folding is simpler if no other constraint type adds a similar enum (the Element/Isotope variants would need parallel constraint-side variants when JointDomain supports them per doc 96's Reserved list). Keeping them separate is more flexible.

## How `Lattice` would interact with `binds`

If `binds` is a stored field on `AtomAst`, the derived `Lattice` impl has to do *something* with it. Three options:

a. **Field-wise on `BTreeMap`** — would require `BTreeMap<String, AtomBindTarget>: Lattice`. It's not, and there's no obvious lattice on map merging.

b. **`#[lattice(skip)]` attribute on the field** — derive ignores `binds`. Then somewhere we have to decide: what should `meet`/`join` do with the binds field? Three plausible answers:
   - Take from `self` (asymmetric, breaks commutativity)
   - Union with conflict-detection (meet returns None on cross-atom id collision with different targets; join takes intersection of identical entries). Most principled.
   - Always take empty (lose all bind metadata on every meet). Wrong.

c. **Hand-roll `AtomAst::Lattice`** — the field-wise body is short; we can write it ourselves to handle binds with the right semantics.

If we go derived + skip, we need to add `#[lattice(skip)]` support to `umol-ast-macros` and decide the skip semantics (union-with-conflict-detection seems right). If we hand-roll, no macro changes needed but we lose the drift-protection benefit of the derive.

## Where invariants are enforced

a. **At construction** — `AtomAst::declare_bind(id, target)` returns `Result`, prevents duplicates. Every site that produces a `Bind` field must also call it. Type-system makes invalid state hard to construct.

b. **Runtime validation** — `AtomAst::validate_binds() -> Result<(), BindError>` called at boundaries (parse, EDN deserialize, programmatic-build entry points). Invalid state is reachable internally but caught at edges. Tests for the validator stand alone from tests for construction.

(b) is less invasive; (a) is more principled but bigger surface change. The Lattice path operating on already-validated AST may temporarily desynchronize binds (e.g., meet result combines two scopes); validator should not be called from `meet`/`saturate`.

## Migration cost

If we adopt stored-field + same-namespace-typed-target:

- Add `AtomAst::binds: BTreeMap<String, AtomBindTarget>` (default empty).
- Add `declare_bind` / `validate_binds` / `with_charge_bind`-style helpers.
- Update `raise_atom` / `lower_atom` exhaustive destructures.
- Sweep tests in `umol-ast/tests/property.rs`, `dsl/atom.rs`, `dsl/value.rs`, `ast/atom.rs`, others.
- Parser: register binds during `apply_predicates`, two-pass for JD resolution.
- Display: `fmt_constraint` JD arm uses `binds` inverse lookup.
- DSL macros (`mol!`, `atom!`, etc.): may need updates.

Rough estimate: 20–50 call sites need touching. Most are tests. Not huge but not trivial.

## Out of scope of this doc

- Cross-atom relational constraints (`MoleculeConstraint::ChargeSum { atoms, sum }` referencing cross-atom binds). The bind scope is a *prerequisite* for these but the constraint design is separate.
- Extending `JointVar` to include `Element`/`Isotope` (the `Reserved` list in `joint_domain.rs`). Independent change.
- Bind-name alpha-renaming on AST transforms. Out of immediate need.
- The `Bind`-id-inside-Bind-variant denormalization question (whether `ValueAst::Bind` should drop its `String` field and look up via scope). Probably keep the id; arguments above.

## Open questions to resolve before implementation

1. **Scope level** (Q1): atom-local only? both with derived molecule view? both with stored molecule scope?
2. **Representation** (Q2): stored field vs derived view?
3. **Namespace** (Q3): one namespace with typed target, or per-type?
4. **`JointVar` vs `AtomBindTarget` relationship**: fold or keep separate?
5. **Lattice handling of `binds`**: derive with skip + union semantics, or hand-roll?
6. **Invariant enforcement timing**: at-construction or runtime-validated at boundaries?
7. **Bind id staying inline on field `Bind` variants**: yes (denormalized) or no (look up via scope)?
8. **Helper ergonomics**: do we add `with_charge_bind(id, set)` sugar, or require callers to chain `with_charge(Bind(...)).declare_bind(...)`?

Each answer feeds the next; settle the top ones first.
