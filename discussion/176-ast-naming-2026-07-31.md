# 176 — Naming of AST types, traits, and the entity payload key

Status: Proposed
Date: 2026-07-31
Relates: [172](172-ast-literal-extraction-2026-07-30.md),
[173](173-ground-literals-and-spin-2026-07-30.md),
[175](175-ground-ast-api-2026-07-31.md)

Not agreed. This records the proposal, the measurements it rests on, and the alternatives that were
considered and rejected, so the whole thing can be judged at once rather than a piece at a time.

## What `Ast` currently means

The suffix carries two unrelated ideas that happen to have been introduced at different times:

1. **Raise/lower.** The original use. `umol-ast` holds the explicit model, the way a compiler holds
   an AST; boundary types (`AtomDsl`, `MoleculeDsl`) and external formats convert into it. This
   motivates the word.
2. **Lattice.** Noticed later. A type with a `Lattice` impl admits indeterminate values, sets,
   wildcards and variables.

The two were assumed to coincide. **They almost do.** Measured 2026-07-31:

- 35 `*Ast` types in `umol-ast`.
- 32 implement `Lattice`, mostly by derive.
- 3 do not: `MoleculeAst`, `ReactionAst`, `ReactionSpanAst`.

So the suffix is accurate for 32 types and inaccurate for exactly 3 — and those 3 are the primary
types a user meets first. 44 `*Ast` types are exported to `umol-py`, so this is chemist-facing
naming, not an internal detail.

## Proposal

| Change | Rationale |
| --- | --- |
| `MoleculeAst` → `Molecule`, `ReactionAst` → `Reaction`, `ReactionSpanAst` → `ReactionSpan` | Not lattice types, and they are *the* types. A discriminator carried by every element discriminates nothing. |
| `AtomAst`, `BondAst`, `ElementAst`, … keep `Ast` | With the 3 removed, `Ast` means exactly "lattice-shaped, and the target of raise/lower" — one coherent property rather than two conflated ones. |
| `IntoAst` → `Raise`, `FromAst` → `Lower` | The traits stop naming a type family that may be renamed again. Raising adds structure at the boundary; lowering returns to the surface form. |
| `ValueAst` → `NumAst` | `Value` is wrong: elements are values too. The type is numeric. Artifact of an earlier iteration. |
| `ValueTerm` → `ArithExpr` | It is `Lit \| Var \| Neg \| Sum \| Product \| Div \| Rem` — an arithmetic expression. |
| `ValuePredicate` → `PredExpr` | Parallel to the above; the two are the sub-languages of `NumAst`. |
| `umol-ast` crate name unchanged | Least visible name, largest churn. Python users never see it; Rust users see one `use` line. |

`NumAst` / `ArithExpr` / `PredExpr` must land atomically: `NumAst::Term(Box<ArithExpr>)` means the
old `ValueTerm` name is freed and reused in the same change, and any intermediate state has
`ValueTerm` meaning two things.

## Alternatives considered and rejected

### Strip the suffix from all 32 as well

Rejected. `Element` (`umol-chem`), `UnpairedElectrons` (`umol-chem`), `StereoConfiguration`
(`umol-ast`) and the doc 173 carriers (`IsotopeMass`, `AromaticValence`, `MulticenterValence`,
`TetrahedralStereo`, `CisTransStereo`) already hold the plain names as concrete domain types. The
lattice versions need some distinguishing word, and once some need it, all should have it.

Sixteen `*Ast` types would collide with an existing plain type. Eleven are genuine
lattice/carrier pairs. Five — `Atom`, `Bond`, `MulticenterBond`, `Molecule`, `Reaction` against
`umol_io::table_ir` and `umol_geometric` — are cross-layer and would be tolerable on their own.

### Suffix only where a carrier competes

Rejected, and this is the decisive argument. It would give `Atom` (a lattice type) beside `Element`
(a concrete type with `ElementTerm` as its lattice). The bare name would mean "lattice" for one and
"ground" for the other, so a reader must already know the type to decode its name. Worse than either
uniform choice.

### `*Term` for the lattice types

Rejected. Semantically the most accurate word — these are terms with variables, and "ground term" is
already the project's vocabulary — but applied uniformly it produces `AtomTerm`, which sits directly
on atomic term symbols from spectroscopy. The word only looked safe while entity types were exempt,
and that exemption is what the previous item rejects.

### `*Spec` for the lattice types

Viable, not chosen. `AtomSpec`, `ElementSpec`, `AromaticValenceSpec`: no chemistry collision, and
"specification" carries the may-be-partial sense with a fully specified one being ground. Costs a
35-type rename and a new word, against `Ast` which is already there and, once the 3 are removed,
already correct. Reconsider only if retiring the programmer jargon is judged worth that churn on its
own.

### Encoding lattice-shape in the name at all

Reconsidered and largely abandoned. 32 of 35 types are lattice-shaped; marking that is not a
distinction. The reason to keep a suffix is narrower: the plain names are already taken by concrete
domain types. That is a collision argument, not a semantic one.

## Open: the `:type` key in entity definitions

```clojure
:aromatic-systems [{:atoms [0 1 2 3 4] :type "[1,1,1,1,1]#c-"}]
:bonds            [[0 1 "1#a"]]
```

`:type` names the entity's attribute string — element or order or electron counts, followed by
`#`-tagged predicates.

**The no-backward-compat policy covers the on-disk notation too, not only the API** (author,
2026-07-31), so this is decided on merit alone. Stored EDN, fixtures, the DSL specification and the
whitepaper figures all move with it; none of that is an argument against.

Against `:type`:

- It is not a type in any sense the rest of the vocabulary uses. The paper and the code use **kind**
  for what distinguishes an aromatic system from a dative bond, so `:type` reads as a near-synonym of
  something it is not.
- What it holds is the entity's inherent fields and constraints. The paper's umbrella term for those
  two together is **attributes** (§6 opens "An entity carries attributes of two kinds"), and the
  string sublanguage is described there as the attribute string.

Candidates:

| key | for | against |
| --- | --- | --- |
| `:spec` | short; carries the may-be-partial sense; pairs with `Spec` if that ever becomes the type suffix | introduces a third word for what the paper already calls attributes |
| `:attributes` | the paper's own umbrella term; matches house style, which uses full hyphenated words throughout (`:aromatic-systems`, `:ring-membership`, `:ligands`) and has no abbreviations | long, and it appears on nearly every entity |
| `:attrs` | short and still the paper's word | would be the only abbreviated key in the notation |

Recommendation: `:attributes` if the notation's full-word house style is held to, `:attrs` if brevity
wins at this frequency. `:spec` only if `Spec` also becomes the type suffix, so that one word covers
both — otherwise it adds vocabulary for no gain.

Note that the positional forms carry the same payload with no key at all (`[0 1 "1#a"]`), so the key
appears only in map forms and the frequency cost is lower than the 20 occurrences in the
specification suggest.

## Notes

- The three renamed types are the ones that appear first in the Python API and in the whitepaper
  primer, so the change is worth most where it is cheapest.
- Doc 173 and doc 175 are already rewriting these types. If the renames happen, they should ride
  along rather than follow, to avoid a second repository-wide sweep.
- No external consumers beyond alpha testers; repository policy is no backward compatibility.
