# 176 — Naming of AST types, traits, crate, and the entity payload key

Status: Proposed
Date: 2026-07-31
Relates: [172](172-ast-literal-extraction-2026-07-30.md),
[173](173-ground-literals-and-spin-2026-07-30.md),
[175](175-ground-ast-api-2026-07-31.md)

The implementation scope covers the complete naming migration settled below. Historical alternatives
remain in the document to preserve the analysis that led to the selected names, but they are not
implementation options.

## Implementation scope

The graph intermediate-representation layer is renamed consistently in Rust and Python:

- the `umol-ast` crate becomes `umol-graph-ir`, with `umol_graph_ir` as its Rust import name;
- the public and source `ast` module becomes `ir`;
- the companion procedural-macro and fuzz packages become `umol-graph-ir-macros` and
  `umol-graph-ir-fuzz`;
- `FromAst`, `IntoAst`, `TryFromAst`, and `TryIntoAst`, including their methods, become the
  corresponding `*Ir` traits and methods;
- every lattice type with an `*Ast` suffix is renamed to `*Form`;
- `ValueAst`, `ValueTerm`, and `ValuePredicate` become `NumForm`, `ArithExpr`, and `PredExpr`;
- the private non-lattice `PredicateForm` helper becomes `PredicateReduction`;
- the three non-lattice aggregates become `Molecule`, `Reaction`, and `ReactionSpan`; and
- the entity-map key `:type` becomes `:attrs`.

`Molecule`, `Reaction`, and `ReactionSpan` are the only current `*Ast` types that do not implement
`Lattice`. They are complete graph-model objects rather than lattice-shaped forms, and no same-layer
concrete carrier competes for their bare names. Role-bearing names such as `MoleculeEntries`,
`ReactionSpanEntries`, the `*Dsl`, `*Defaults`, `*Metadata`, update, delta, edit, and error types keep
their suffixes. The rejected `*Def` alternative therefore does not trigger a `*Defaults` to
`*Presets` migration, and `*Overrides` also remains unchanged.

The separately approved `Ctx` to `Context` associated-type migration remains owned by doc 186 and is
not duplicated here. The whitepaper is explicitly excluded from the repository sweep and will be
updated separately by the author.

The `ast` to `ir` module rename preserves the existing export topology: symbols exported through
`umol_ast::ast` move to `umol_graph_ir::ir`. Whether any of them should additionally be re-exported
from the crate root is a separate API-design question, not part of this naming migration.

The migration is breaking and supplies no compatibility crate, module, trait, type, method, DSL-key,
or Python aliases. Rust import aliases remain available where another layer has its own `Molecule`
or `Reaction`; in `umol-py`, Rust imports use the crate-derived `GraphIr` prefix rather than
preserving `Ast` in internal aliases.

## What `Ast` currently means

The suffix carries two ideas introduced at different times:

1. **Raise/lower.** The original use. `umol-ast` holds the explicit model the way a compiler holds an
   AST; boundary types (`AtomDsl`, `MoleculeDsl`) and external formats convert into it.
2. **Lattice.** Noticed later. A type with a `Lattice` impl admits indeterminate values, sets,
   wildcards, and variables.

Measured 2026-07-31:

- 35 `*Ast` types in `umol-ast`; 32 implement `Lattice`, mostly by derive.
- The 3 that do not are `MoleculeAst`, `ReactionAst`, `ReactionSpanAst`.
- 44 `*Ast` types are exported to `umol-py`. This is chemist-facing naming.
- **1 of 30 is recursive**: `ValueAst`, via `Box<ValueTerm>` and `Box<ValuePredicate>`.

The last figure is the one that matters for the name. There is nesting — `MoleculeAst` holds
`AtomAst` holds `ValueAst` — but the depth is fixed by the schema, not by the input. A molecule is
always molecule → entity → attribute, and no input can make it deeper. Only `ValueAst`'s arithmetic
and predicate arms admit unbounded nesting. That is a record hierarchy over lattice-valued leaves with
one embedded expression language, which is a schema, not a grammar.

**So the structural claim in the name is false for 29 of 30 types.**

## What the suffix is actually for

One reason, and it is a good one: **disambiguating the lattice type from the concrete carrier of the
same name.** `ElementAst::Lit(Element)` puts both in one expression, so they cannot share a name.
Eleven such pairs exist today — `Element`, `UnpairedElectrons`, `StereoConfiguration`, plus the doc
173 carriers `IsotopeMass`, `AromaticValence`, `MulticenterValence`, `TetrahedralStereo`,
`CisTransStereo`, and probably `NoncovalentBondKind`, `Stereogenicity`, `Topicity`.

Inverting it — plain names for the lattice types, qualified names for the carriers — fails, because
`umol_chem::Element` is a fundamental domain type that should not move, and
`Element::Lit(Element)` is worse than what we have.

Every other justification offered for `Ast` is post-hoc. The pipeline role is already carried by the
crate name and by the conversion traits; it does not need restating on thirty types.

If disambiguation is the only job, the criterion is simply the most accurate word that does it, and
`Ast` fails that test on the measurement above.

## Recommendation

| Change | Rationale |
| --- | --- |
| `MoleculeAst` → `Molecule`, `ReactionAst` → `Reaction`, `ReactionSpanAst` → `ReactionSpan` | Not lattice types, no competing carrier, and they are *the* types. A discriminator carried by every element discriminates nothing. |
| lattice `*Ast` → `*Form` | A uniform suffix with one enforceable rule: these types implement `Lattice`. |
| crate `umol-ast` → `umol-graph-ir` | "Intermediate representation" is accurate for the family and commits to nothing about shape. In-project precedent: `umol_io::table_ir`. |
| module `ast` → `ir` | Avoids retaining the rejected structural claim inside the renamed crate path. |
| `IntoAst` → `IntoIr`, `FromAst` → `FromIr` | Keeps Rust's `Into`/`From` idiom, so direction is obvious without new vocabulary. Names the stable family rather than the type suffix. |
| `ValueAst` → `NumForm` | `Value` is wrong: elements are values too. The type is numeric. |
| `ValueTerm` → `ArithExpr`, `ValuePredicate` → `PredExpr` | `Lit \| Var \| Neg \| Sum \| Product \| Div \| Rem` is an arithmetic expression; the two are the sub-languages of `NumForm`. |
| private `PredicateForm` → `PredicateReduction` | It is the result of reducing a predicate to top, bottom, or a remaining predicate, not a lattice form. |
| notation key `:type` → `:attrs` | Same decision as the type suffix, not a separate one — see below. |

The division of labor: the **crate** names the family as an intermediate representation, which is
true of the ensemble; the **traits** name the transitions; the **types** say what each one
individually is. Nothing claims to be a tree.

## The `:type` key

```clojure
:aromatic-systems [{:atoms [0 1 2 3 4] :type "[1,1,1,1,1]#c-"}]
```

`:type` holds the entity's attribute string. It is wrong for the same reason the suffix is: the
project uses **kind** for what distinguishes an aromatic system from a dative bond, so `:type` reads
as a near-synonym of something it is not.

The key here plays a related but distinct role from the type suffix. The atom *attributes* are
represented by an AtomForm, however, the attributes refer to entities only, while Forms exist for
individual attributes but also constituent parts of attributes.

The no-backward-compat policy covers the on-disk notation, not only the API (author, 2026-07-31), so
stored EDN, fixtures, the DSL specification, and the whitepaper figures moving with it is not an
argument against.

## Search for a replacement suffix

**`Spec` is out** (author). A spec is *prescriptive* — a blueprint with one intended output. These
types are *descriptive*: statements about which values qualify, admitting many. The suffix picks the
wrong relation.

That objection generalizes. The descriptive-side vocabulary is spoken for in this domain:
`Descriptor` is a computed property, `Predicate` is forbidden by doc 177 for the stored object and
claimed by `PredExpr` here, `Class` is stereo `ClassKey`, `Domain` is constraint-satisfaction,
`Filter` and `Selector` imply query use that ground values do not have. `Description` alone survives
and is eleven letters.

**The finding after exhausting the space: no available word names partiality without colliding.**
Chemistry and Rust have spent the relevant vocabulary between them, and `Atom` collides with whatever
is left — `AtomTerm` (term symbols), `AtomIr` (infrared), `AtomOpen` (open shell), `PseudoAtom`
(MOL placeholder, and `pseudonode` internally). Test any future candidate against `Atom` first.

**Which argues for a semantically light marker rather than a meaningful one.** A tag that asserts
nothing beats a word that asserts something false, and `Ast` asserts something false for 29 of 30
types.

### Crate rename: `umol-ast` -> `umol-graph-ir` (2026-08-02, author-proposed)

Separable from the type-suffix question and probably a precondition for settling it well.

The author's own characterization: **`umol-ast` is the IR for the graph model, no more and no less.**
The name should say so. `umol-io` already establishes `table_ir` as the repository's word for a
boundary representation, so `graph-ir` is consistent with an existing and well-justified name rather
than a new coinage.

It also fixes a misreading the four-domains discussion (doc 015, doc 180) kept having to correct:
`umol-ast` does not look like it belongs to the graph model class. Renamed, the family reads:

```
umol-graph-core   the graph data structure
umol-graph-ir     the graph model's IR          (was umol-ast)
umol-graph        operations over it
```

and the layering reads honestly end to end: **format -> table IR -> graph IR**, two intermediate
representations at two layers, each named for what it is.

**Why this makes the suffix question easier.** `Ast` has been hard to replace because it carried two
claims at once — the layer ("this is the intermediate representation") and partiality ("this value
may be underdetermined"). No single suffix serves both, which is why every candidate failed on one
axis or the other. Moving the layer claim onto the crate name leaves the suffix one job.

Note `Ir` failed as a *type* suffix because `AtomIr` reads as infrared. It does not fail as a crate
name: `umol-graph-ir` has no chemistry collision.

**Timing.** Nothing is published but the `umol` 0.0.0 placeholder, so this is a mechanical
workspace-wide rename now. Repository policy supplies no compatibility shim. It is as cheap as it
will ever be.

### `*Form` — selected (2026-08-03)

`AtomForm`, `ElementForm`, `IsotopeMassForm`, `AromaticValenceForm`. Four letters.

**The substrate argument, which is the load-bearing one.** In mathematics *form* is never
freestanding — bilinear form, quadratic form, differential form, normal form. The qualifier carries
the meaning and the word itself carries almost none, which makes it a neutral substrate on par with
*element*, *term*, *expression*, *shape*. `AtomForm` therefore reads as *the form of an atom*, and no
reader derives a specific mathematical form from it any more than they confuse a bilinear form with a
normal form. Polysemy here is evidence of neutrality rather than of ambiguity — the opposite of how
an earlier round of this document scored it.

For the same reason, attempting to exclude *resonance form*, *tautomeric form* or *atomic form
factor* is asking too much of any word. The term is never used without saying what it is a form of.

**Why it beats each surviving alternative:**

| loses to `Form` | because |
| --- | --- |
| `Ast` | `Form` is an ordinary word, and the syntax-versus-value distinction that `Ast` gets wrong is an extremely strict test |
| `Term` | atomic terms in spectroscopy; `Form` also feels more colloquial without being so |
| `Def` | `Def` is a real word only by appeal to Python syntax; `Form` is a real word outright |
| `Q` | `Q` communicates nothing; `Form` communicates something |

**It is the first candidate that positively names partiality.** A form has blanks: an unfilled form is
a partial specification and filling it in makes it concrete. Every earlier candidate merely avoided
misdescribing partiality; none said it. This sense reaches every reader without a glossary, in four
letters.

**It also repairs the `Element` wart.** `Element` is concrete while its lattice counterpart is
separate, which this document earlier recorded as "a really ugly complication". `Element` /
`ElementForm` reads cleanly — the element, and the form an element description takes. Compare
`ElementDef`, which suggests a definition *of the chemical element* rather than a description of
which elements qualify. `Form` is the only candidate whose leaf case reads better than its entity
case, and the leaves are where the wart was.

**The Platonic objection is withdrawn.** That a Platonic Form is more determinate than its instances,
while these values are less determinate than theirs, is a comically high bar — a Platonic ideal of a
term, as the author put it. No word will satisfy every criterion, except perhaps `*LatticeMember`,
and `AromaticValenceLatticeMember` is its own refutation.

#### The rule: the suffix marks a `Lattice` implementation

**`*Form` means the type implements `Lattice`** (author, 2026-08-03). This makes the suffix carry
information rather than decorate, and it retroactively justifies the three bare names already
proposed in this document: `Molecule`, `Reaction` and `ReactionSpan` drop the suffix precisely
because they do not implement `Lattice`.

Consequence: **`PredicateForm` must be renamed.** `umol-ast/src/ast/value.rs:284` defines a private
`enum PredicateForm { Top, Bottom, Predicate }` — the canonical reduction of a predicate, not a
lattice type. Being private and confined to one file, the effort is well below the `Defaults` rename
that `Def` would have required.

#### The EDN map key: `:attrs`

**Selected for this migration.** The alternatives considered were:

- **`:attrs`**, preference, describes the purpose of the entry not its shape.
- **`:form`**, alternative, matches the suffix and answers the natural question directly: what is the type
  of the aromatic system? An `AromaticSystemForm`. A term of art in the DSL, which is what `:type`
  already was.
- **`:type`**, backup, and "would not be horrible" (author). Against it: *type* is
  already spoken for, since atom typing is the valence model (`ValenceModel::AtomTyping`), so the DSL
  key and the conformance mechanism would share a word while meaning nothing alike. The same class of
  defect as `Ast`.
- **`:spec`** — rejected (author, 2026-08-03), and not to be raised again.

**Blast radius, measured 2026-08-03**, so the cost is known when this is picked up:

| site | occurrences |
| --- | --- |
| spec (`umol-dsl-spec.md`) | 45 |
| resolution snapshots | 45 |
| Rust sources (`"type"`) | 39 |
| whitepaper `main.tex` | 12 |
| resolution conformance corpus (653 case files) | **0** |

The corpus is untouched because those cases carry `:config-overrides` rather than entity `:type`
keys. Snapshots regenerate. So this is roughly a hundred mechanical edits plus a snapshot refresh —
cheap now, and cheaper than it will be after 0.6 ships.

`Format` proximity was considered and dismissed: two letters of difference, and visible enough.

**Status: selected.**

### `*Def` — superseded candidate (2026-08-01)

`AtomDef`, `ElementDef`, `IsotopeMassDef`. Three letters, same length as `Ast`.

**Why it clears the bar `Spec` failed.** `def` is the function-*definition* keyword in Python, so the
suffix reads as "definition" to the primary audience, and **a definition may be partial** — it says
what a thing is without having to finish the job, where a spec implies something to be built to. This
is the descriptive/prescriptive distinction that killed `Spec`, and `Def` lands on the right side.

Passes the `Atom` test: `AtomDef` collides with no chemistry term.

**Price: renaming the `Defaults` family.** Twenty types in `umol-ast/src/dsl/config.rs` and its
callers — thirteen plural `*Defaults` structs and seven singular `*Default` enums — roughly a
thousand occurrences. The singular ones collide worst, `Default` being four letters from `Def`:

| new | existing |
| --- | --- |
| `AromaticValenceDef` | `AromaticValenceDefault` |
| `MulticenterValenceDef` | `MulticenterValenceDefault` |
| `AtomDef` | `AtomDefaults` |

**Why the price is worth paying, and why this collision is unlike the others.** Every previous
candidate died against something outside our control — term symbols, infrared, `os.PathLike`,
pseudoatoms, `SubstitutionCount`. This one is a single internal config module and a mechanical
rename. "We cannot have the right external suffix because of an internal struct" is the wrong trade.

The external surface is unaffected either way: only `MoleculeDefaults` (22 uses) and
`ReactionDefaults` (20) reach Python, and both belong to entities that lose the suffix entirely under
this document, so the public API would read `Molecule` beside `MoleculeDefaults`.

**Replacement name: `*Presets`.** `Defaults` is genuinely apt, which is the real cost — the struct
fills unspecified attributes on read *and* tells the renderer which values it may omit.

`*Fill` / `*Fills` describes one member more exactly (it is a fill-in, and `fill` has no type-level
claim in the codebase — 34 occurrences, all lowercase locals). **But `Defaults` does not travel
alone.** It pairs with the `Overrides` family, and the two appear in a single expression:

```rust
// umol-graph/tests/resolution/mod.rs:110
let defaults = MoleculeDefaults::default().with_overrides(test_input.config_overrides);
```

Base plus patch. `Presets`/`Overrides` is an idiomatic pair; `Fills`/`Overrides` is not — one
overrides a default, not a fill. The pairing governs, so `*Presets` wins over the more exact
`*Fill`. It is also already used informally for this concept at
`umol-ast/src/ast/molecule/build.rs:227` (`preset_charge_preserved`); against that, it also names the
SMILES and CTfile capability presets.

**`Overrides` stays.** No collision with `Def`, and the family is small — ten types, ~75 occurrences
against `Defaults`' ~1000: `AtomOverrides` (10), `MulticenterBondOverrides`, `BondOverrides`,
`AromaticSystemOverrides` (8 each), `StereoAtomOverrides`, `StereoBondOverrides`,
`NoncovalentBondOverrides`, `DativeBondOverrides`, `MoleculeOverrides` (6 each), `ReactionOverrides`
(3).

**`Overrides` is load-bearing in the conformance suite,** which constrains any rename of its
partner. `MoleculeOverrides` is the per-case input field (`mod.rs:24`, `#[edn(default)]`), and **all
653 resolution conformance cases set `:config-overrides`** — every case patches the defaults rather
than accepting them. The shapes in use:

| cases | override |
| --- | --- |
| 273 | `{:atom {:aromatic-valence :not-aromatic :charge :zero}}` |
| 129 | `{:atom {:implicit-hydrogens :zero :charge :zero}}` |
| 127 | `{:atom {:implicit-hydrogens :zero}}` |
| 87 | `{:atom {:aromatic-valence :not-aromatic :charge :zero :implicit-hydrogens :zero}}` |
| 37 | remaining combinations of the same three keys |

A `Defaults` rename therefore touches 653 corpus files only if the EDN key changes; the key is
`:config-overrides` and is unaffected.

### `*Sub` — rejected

Charming as the Fortran/Perl counterpart to Python's `def`, and dead on contact. `sub` is the most
loaded prefix in the codebase: `SubgraphIsomorphismAlgorithm` (196), `SubstructureMatchAlgorithm`
(143), `subgraph` (92), `SubPatternAnchor` (83), `SubstitutionCount` (62), `subgrammar` (64),
`substructure` (41). `SubstitutionCount` alone is fatal — a per-atom chemical attribute that
`AtomSub` would sit beside meaning something unrelated. None of these are removable.

### `*Q` — superseded candidate

`AtomQ`, `ElementQ`, `IsotopeMassQ`. One character; two shorter than `Ast`.

- Makes no claim, so nothing about it can be wrong — the class of answer the search converged on.
- Survives every collision that killed the others.
- Precedented in shape if not in letter: Common Lisp marks predicates with `p` (`numberp`, `listp`),
  Scheme with `?`, and Haskell and Scala use `T` for monad transformers (`OptionT`, `StateT`). A
  single character with a locally documented meaning is an established move.
- Mnemonic: question, and whimsy.

Cost: a reader meeting `AtomQ` cold learns nothing from it. But neither does a chemist meeting
`AtomAst`, and `Ast` additionally tells them something untrue.

### Also considered in the same pass

- **`Attr` / `Attrs`** — misdescribes granularity. `AtomAttr` reads as *one attribute of an atom*,
  but the type is the whole atom record. Fits the leaves, breaks on the entities.
- **`Pred`** — doubly spoken for: doc 177 forbids `predicate` for the stored object, and `PredExpr`
  is proposed above for `ValuePredicate`.
- **`Ish`, `let`, `Like`, `Pseudo`, `Open`** — see below and the rejected list.

## Alternatives considered

### Pragmatism: keep `Ast` because it is already there

The honest form of the argument. `Ast` appears on 35 types, 44 Python exports, the DSL
specification, fixtures, examples, snapshots, benchmarks, and the whitepaper. The name is imprecise
but has not actually misled anyone in practice, and imprecision that nobody trips over is cheap.
Churn costs review bandwidth and carries the risk of a botched sweep, and docs 173 and 175 are
mid-flight, so a rename enlarges the blast radius of a change that is already large.

Set aside for two reasons. Repository policy is no backward compatibility, and the only external
users are alpha testers who are colleagues — the conditions under which this is cheapest it will ever
be. And "it is already there" is the definition of the historically-tinged, semantically-inaccurate
usage this project has said it would rather not ossify. The cost is real; it is judged tolerable.

### `*Term` for the lattice types

Semantically the most accurate word — these are terms with variables, and "ground term" is already
project vocabulary. Rejected because applied uniformly it produces `AtomTerm`, which lands on atomic
term symbols from spectroscopy. It only looked safe while entity types were exempt from the suffix,
and that exemption is rejected below.

### `*Ir` for the lattice types

Rejected, and it is worse than it looks. **IR means infrared to every chemist**, and 44 of these
types are in the Python API. `AtomIr` and `BondIr` read as spectroscopy far more strongly than
`AtomTerm` does. The collision is mild at crate level, where chemists rarely look, and severe at type
level. Hence `umol-ir` as a crate with `*Spec` types rather than `*Ir` throughout.

### Strip the suffix from all 35

Rejected. Eleven lattice types have concrete carriers already holding the plain name, and the
carriers cannot move. Five further collisions — `Atom`, `Bond`, `MulticenterBond`, `Molecule`,
`Reaction` against `umol_io::table_ir` and `umol_geometric` — are cross-layer and tolerable on their
own.

### Suffix only where a carrier competes

Rejected, and this was the decisive argument against the earlier draft. It gives `Atom` as a lattice
type beside `Element` as a concrete type with `ElementSpec` as its lattice. The bare name would mean
"lattice" for one and "ground" for the other, so a reader must already know the type to decode its
name. Worse than either uniform choice.

### `*Like` for the lattice types

Considered 2026-08-01 and rejected, though it is the only candidate that gestures at partiality.

`*Like` is unused in the codebase but not unclaimed in meaning. In Python it denotes *convertibility*
— `os.PathLike`, and for this audience decisively `numpy.ArrayLike`, a union of input types that may
stand in where an array is expected.

umol already has that concept under another name. `AtomArg` is "create a fresh atom or reference one
already introduced — what you write picks the variant by type", which is `ArrayLike` exactly, and the
family has four members: `AtomArg`, `BondArg`, `PortArg`, `StereoLigandArg`. So `AtomLike` would name
the wrong type: a Python-fluent reader expects the thing accepting a string or an index and receives a
lattice value.

It also misdescribes slightly. Resemblance and partiality are different relations — a wildcard is not
atom-*like*, it is an atom description that has not committed.

### None of the candidates names partiality

Observed 2026-08-01. The shortlist describes where a type sits or what kind of object it is, never
the property that actually distinguishes these types from their carriers:

- `Ast` and `Ir` — position in the pipeline;
- `Term` — the algebraic object;
- `Spec` — a description, which implies possible partiality without stating it.

What all of these types have in common is that they may be *partly* specified: a wildcard commits to
nothing, a literal commits to everything, and the order between them is the subject of
\Cref{sec:lattice}. A suffix naming that property would be the most informative of the options; none
of the candidates is one, and `Spec` is the nearest.

Not an argument for a new candidate. A note on what the existing ones do not say, so the point does
not have to be re-derived when this document is next opened.

### Encoding lattice-shape in the name

Abandoned. 32 of 35 types are lattice-shaped; marking that marks nothing. The reason to keep a suffix
is collision, not semantics.

### `Raise` / `Lower` for the traits

Viable, and preferred in an earlier draft. Set aside for `IntoIr` / `FromIr`, which keeps the Rust
idiom so the direction needs no explanation, and avoids the question of whether moving toward surface
syntax is "lowering" — in compilers, lowering moves toward the machine.

## Cost of the complete migration

The migration is repository-wide. Its implementation must sweep the DSL
specification, unit tests, property-test strategies, conformance suites, fuzz targets and seed
corpora, fixtures, examples, benchmarks, snapshots, Python tests, and the whitepaper figures and
listings. The notation key change additionally invalidates stored EDN. The whitepaper remains an
author-owned exception to the repository sweep.

Docs 173 and 175 already rewrote some of these types. Their current surfaces are included in this
migration and its final audit.

## Notes

- The three types losing the suffix entirely are the ones a user meets first, in both the Python API
  and the whitepaper primer, so that part of the change is worth most where it is cheapest.
- The crate rename changes `umol_ast::ast` to `umol_graph_ir::ir` without adding crate-root
  re-exports. Export flattening is a separate API-design question.
- No external consumers beyond alpha testers; repository policy is no backward compatibility.

## Staged implementation plan

The migration is deliberately staged by naming family. Each breaking declaration change and its
caller migration belong to the same stage, and the workspace must be green at every stage boundary.
Tests retain their existing cases and assertions; identifiers are renamed when they encode a retired
API name, without using the migration as a test-cleanup pass. No compatibility aliases or legacy
parsing branches are introduced.

### S0 — Crate, package, and module identity

- **S0a — workspace packages: rename the graph-IR crates.** **Done.** Rename the `umol-ast`,
  `umol-ast-macros`, and `umol-ast-fuzz` packages and directories to `umol-graph-ir`,
  `umol-graph-ir-macros`, and `umol-graph-ir-fuzz`. Update workspace membership, excluded fuzz
  workspaces, path dependencies, feature references, package descriptions, Cargo lock data, and
  repository scripts that address the packages by name. Preserve the `mol!` and `frag!` macro
  names. This is breaking and leaves imports red until S0c. `[dep: —]`
- **S0b — `umol-graph-ir`: rename `ast` to `ir`.** **Done.** Rename `src/ast.rs`, its source subtree, the
  public module declaration, internal module paths, module documentation, and generated
  procedural-macro paths from `ast` to `ir`. Preserve the current export topology: the public path
  becomes `umol_graph_ir::ir`, with no new crate-root re-exports and no `ast` compatibility module.
  This is breaking and remains red until S0c. `[dep: S0a]`
- **S0c — workspace consumers: restore imports.** **Done.** Migrate every Rust consumer to the
  `umol_graph_ir` crate and `ir` module, including `umol-graph`, `umol-io`,
  `umol-geometric-graph`, `umol-py`, procedural-macro expansions, tests, UI cases, binaries,
  examples, benchmarks, fuzz targets, and scripts. Python-binding imports use the crate-derived
  `GraphIr` prefix where aliases are required. Run package tests, macro expansion/UI tests, and
  compile every workspace target. This is breaking, red to green. `[dep: S0b]`

### S1 — IR conversion traits

- **S1a — `ir::traits`: rename the infallible conversion pair.** **Done.** Rename `FromAst`/`from_ast` and
  `IntoAst`/`into_ast` to `FromIr`/`from_ir` and `IntoIr`/`into_ir`. Migrate every implementation,
  bound, call site, macro expansion, rustdoc reference, unit test, property strategy, benchmark,
  fuzz target, and downstream crate in the same subitem. Keep the associated type named `Ctx`; its
  separately approved `Context` migration remains in doc 186. This is breaking, red to green.
